# 简历项目与作品集

作品集的目标不是证明你使用过多少框架，而是让面试官能沿着一个真实问题，看到你的判断、实现、实验和复盘。

**求职导航**：[岗位路线](roadmap.md) · [面试题](interview-questions.md) · [编码轮](coding-round.md) · [系统设计](system-design.md) · [行为面试](behavioral.md) · [工程项目索引](../practice/project-index.md)

## 面试官真正想确认什么

一个项目至少要回答六个问题：

1. 你解决的用户或系统问题是什么？
2. 最简单基线是什么，为什么不直接停在那里？
3. 你负责了哪一部分，关键取舍是什么？
4. 结果怎样测量，失败样例在哪里？
5. 系统出错、越权或过载时会怎样？
6. 哪些结论只在本地或离线成立？

如果项目介绍只能回答“用了什么”，它仍然是技术清单，不是能力证据。

## 选择一个主项目

一个主项目加一个相邻能力，通常比四个换壳聊天应用更有说服力。

| 求职方向 | 主项目 | 相邻能力 | 面试重点 |
|---|---|---|---|
| LLM 应用 / RAG | 可诊断企业 RAG | 评测门禁 | 召回、引用、权限、失败归因 |
| Agent / 平台 | 可恢复工具 Agent | 云 API 契约 | 状态、授权、幂等、恢复 |
| 模型 / 训练 | 单卡微调 | 数据审计或评测 | labels、基线、held-out、显存 |
| 推理 / 系统 | 单卡推理服务 | Transformers 原理 | TTFT、TPOT、KV、过载 |
| 评测 / 数据 | 模型评测平台 | RAG 或 Agent | case、切片、统计、发布判断 |

项目入口和最小命令见[工程项目索引](../practice/project-index.md)。

## 用一句话讲清项目

推荐句式：

> 在 `[数据、流量、硬件或权限约束]` 下，为 `[用户问题]` 建立 `[基线]`；实现 `[关键机制]`，并用 `[固定评测与失败切片]` 比较结果；最终以 `[安全、容量或发布门禁]` 限定上线范围。

数字只有在能回答分母、环境、基线和原始结果位置时才写入简历。否则先写机制和验收，不要编造精确提升。

## 五种项目怎样做出深度

### 可诊断企业 RAG

先完成：固定小语料上的 BM25、来源展示和无答案拒答。

做深：加入 dense/rerank、租户 ACL、token budget、引用验证、索引更新和分层错误分析。

适合指标：Recall@k、nDCG、引用正确率、拒答、越权负例、端到端延迟。不要用一个总分掩盖“检索正确但生成错误”。

### 可恢复工具 Agent

先完成：模型只生成 typed proposal，执行层独立校验并调用一个只读工具。

做深：加入审批、幂等 ledger、预算、pending 状态、崩溃恢复和独立 completion verifier。

适合指标：带 verifier 的任务成功率、非法参数拒绝、越权 attempt、重复副作用和未解决 pending。模型说“成功”不计为执行成功。

### 单卡微调与推理

先完成：比较 base Prompt 与一份小规模 LoRA 训练，打印最终 input IDs、labels 和监督 token 数。

做深：加入数据切分、rank/target-module 消融、held-out 评测、adapter 重载、量化和目标 GPU 显存记录。

适合指标：任务指标、格式率、通用回归、峰值显存、训练时间和服务吞吐。Loss 下降不是最终质量指标。

### 单卡推理服务

先完成：固定模型、采样配置和请求，记录非流式与流式输出。

做深：区分排队、prefill 和 decode，加入容量上限、取消、过载、prefix cache 和质量回归。

适合指标：offered/dispatch TTFT、TPOT、吞吐、峰值显存和全部请求 outcome。一次延迟不能代表容量。

### 模型评测平台

先完成：固定 case ID、baseline/candidate 输出和一个可重算指标。

做深：加入错误切片、配对比较、judge 校准、人工复核、发布门禁和历史追踪。

适合指标：effect size、区间、切片回归、人工一致性和门禁结果。统计显著不等于业务重要。

## 证据怎样组织

让读者从简历数字逐层下钻：

```text
resume bullet
  -> 项目 README 的结论与边界
  -> summary report
  -> per-case / per-request result
  -> data / workload manifest
  -> code、config 与模型版本
```

作品集首页保持简洁。具体 hash、固定样例数字、完整测试矩阵和内部协议放在 evidence 页面；本仓库自身的
项目表述保留在[作品集 claim 证据台账](../evidence/resume-claims.md)，不作为第一次阅读内容。

## README 推荐结构

1. 问题和使用场景。
2. 五分钟最小运行。
3. 架构图与信任边界。
4. 基线、实验变量和结果。
5. 三个最有代表性的失败样例。
6. 复现环境、已知限制和下一步。

截图用于展示，机器可读结果用于复核。敏感数据使用脱敏或合成样例，并说明它与真实数据的差异。

## 常见扣分项

- 把框架名当作核心贡献。
- 只报最好结果，不提供基线和失败样例。
- 在测试集上反复调参。
- 把 CPU demo 描述成 GPU 或生产性能。
- 写准确率却说不清标签、样本量和分母。
- 把 JSON 可解析、模型完成文本或文件 hash 当作业务正确性。
- 无法区分自己的贡献、框架默认行为和团队已有能力。

## 一页纸的取舍

简历不是完整履历，是一次**筛选材料**。多数技术简历第一遍只被扫 30 秒左右，
所以排版决定了哪些内容会被读到。

大致的空间分配（按目标岗位微调，不是固定比例）：

| 区块 | 大致篇幅 | 判断标准 |
|---|---|---|
| 基本信息与一句话定位 | 2–3 行 | 让人一眼看出你申请的是哪条路线 |
| 主项目 | 最大一块，4–6 条 bullet | 面试官会从这里挑深挖题 |
| 工作经历 | 每段 3–4 条 | 只保留与目标责任域相关的 |
| 相邻项目 | 2–3 条 | 证明你理解上下游 |
| 技能列表 | 尽量短 | 长列表会稀释信号，且每一项都可能被抽查 |

该删掉的：

- **无法下钻的数字**。写不出分母、基线和环境的数字，删掉比留着安全——
  被追问时答不上来的损失，大于这个数字带来的收益。
- **技能清单里的长尾**。列出十五个框架，面试官只会挑你最不熟的那个问。
- **和目标路线无关的旧项目**。留一行说明背景即可，不要占 bullet。
- **课程与证书**。除非该课程有可展示的产出，否则它证明的是投入时间而不是能力。
- **"熟悉"、"精通"这类自评词**。用[能力四级](roadmap.md#ownership-levels)
  的实际证据替代，或者干脆不写。

bullet 的写法、反向审计链和不同证据等级的措辞边界，
见[岗位路线的证据语法](roadmap.md#evidence-levels)，此处不重复。

## 同一段经历，面向不同 JD 怎样改写

改写不是换同义词，而是**换主语**——把叙述重心移到目标岗位首先负责的失败上。

以[岗位路线里那位后端转型的候选人](roadmap.md#worked-example)为例，
同一个"可诊断 RAG"项目，面向两种 JD：

**面向"LLM 应用 / RAG"岗位**，重心在检索质量归因：

> 为企业知识助手构建可诊断 RAG：固定 80 条问题作为回归集，将错误归因到检索、
> 重排、引用和权限四层；在该固定集上把无引用回答从 24 条降到 6 条，
> 并保留全部失败样例。结论限于该离线集合，未覆盖真实用户分布。

**面向"Agent / 平台"岗位**，同一个项目重心在权限与故障边界：

> 为企业知识助手设计多租户检索的权限边界：ACL 过滤在打分之前生效，
> 避免语料级统计量泄漏不可见文档的存在性；重排层独立复核权限，
> 并对越权路径补了故障注入测试。未覆盖跨区域部署与真实 IAM 集成。

两段描述的是同一份工作，但第一段被追问会走向"召回怎么测"，
第二段会走向"权限在哪几层成立"。**你希望被问什么，就把什么写在前面。**

不要为了匹配 JD 而声称没做过的事。改写的是**视角**，不是事实。

## 面试轮次与准备重点

轮次划分因公司而异，下面是常见形态与本板块对应页面：

| 轮次 | 主要在考 | 对应准备 |
|---|---|---|
| 简历筛选 | 责任域是否匹配、数字是否可信 | 本页 |
| 初筛 / HR | 基本匹配、动机、区间 | [行为面试](behavioral.md) |
| 编码轮 | 契约、边界、验证意识 | [编码轮](coding-round.md) |
| 机制 / 深挖轮 | 是否真的理解，边界在哪 | [面试题](interview-questions.md) · [应用与治理题](applied-questions.md) |
| 系统设计 | 需求量化、容量、降级 | [系统设计](system-design.md) |
| 项目深挖 | 能否下钻到原始结果 | 本页 + 项目 README |
| 行为 / 主管轮 | ownership 级别 | [行为面试](behavioral.md) |

准备顺序建议按**你最可能被淘汰的环节**排，而不是按轮次先后。
后端转型的候选人通常卡在机制深挖，算法背景的候选人更常卡在系统设计和工程边界。

## 拿到 offer 之后怎样比较

薪资数字最容易比较，也最容易主导决策。但影响长期结果的往往是另外几项：

| 维度 | 要问清楚的 | 为什么重要 |
|---|---|---|
| 责任范围 | 你 own 的是模块、闭环还是跨系统 | 决定下一份工作能讲什么故事 |
| 失败可见性 | 能否拿到线上 badcase 与真实评测 | 拿不到就很难积累可验证的证据 |
| 职级与口径 | 同一 title 在不同公司的范围差异 | title 不可跨公司比较，责任范围可以 |
| 团队稳定性 | 这个方向的资源承诺有多久 | 项目中途取消会让经历难以讲述 |
| 学习面 | 你会接触到哪些以前没做过的失败类型 | 这是唯一会随时间增值的部分 |

其余评估团队的问题见[岗位路线的反向评估](roadmap.md#reverse-evaluation)。

关于谈判，只说三点可迁移的：

- **信息不对称主要在职级映射上**，而不在数字。先弄清对方的职级体系，
  再讨论数字；职级定错，后续调整通常比涨薪更难。
- **区间比精确数字安全**，但区间要基于你了解的市场行情，
  而不是当前薪资的固定倍数。
- **能谈的不止薪资**。到岗时间、方向、汇报关系有时比数字更影响你实际能做什么。

这些不构成任何具体建议——地区、行业和公司阶段差异极大，最终仍以你掌握的实际信息为准。

## 面试前自查

随机选择简历中的一个数字，确认自己能在五分钟内找到它的数据、配置、原始结果和最差样例。然后回答：如果重做，最先增加哪个反例或控制变量？

能回答并展示证据，项目才真正属于你；不能回答时，删掉数字或补做实验。
