# 简历项目与作品集

作品集的目标不是证明你使用过多少框架，而是让面试官能沿着一个真实问题，看到你的判断、实现、实验和复盘。

**求职导航**：[岗位路线](roadmap.md) · [面试题](interview-questions.md) · [系统设计](system-design.md) · [工程项目索引](../practice/project-index.md)

## 面试官真正想确认什么

一个项目至少要回答六个问题：

1. 你解决的用户或系统问题是什么？
2. 最简单基线是什么，为什么不直接停在那里？
3. 你负责了哪一部分，关键取舍是什么？
4. 结果怎样测量，失败样例在哪里？
5. 系统出错、越权或过载时会怎样？
6. 哪些结论只在本地或离线成立？

如果项目介绍只能回答“用了什么”，它仍然是技术清单，不是能力证据。

## 选择一个主项目

一个主项目加一个相邻能力，通常比四个换壳聊天应用更有说服力。

| 求职方向 | 主项目 | 相邻能力 | 面试重点 |
|---|---|---|---|
| LLM 应用 / RAG | 可诊断企业 RAG | 评测门禁 | 召回、引用、权限、失败归因 |
| Agent / 平台 | 可恢复工具 Agent | 云 API 契约 | 状态、授权、幂等、恢复 |
| 模型 / 训练 | 单卡微调 | 数据审计或评测 | labels、基线、held-out、显存 |
| 推理 / 系统 | 单卡推理服务 | Transformers 原理 | TTFT、TPOT、KV、过载 |
| 评测 / 数据 | 模型评测平台 | RAG 或 Agent | case、切片、统计、发布判断 |

项目入口和最小命令见[工程项目索引](../practice/project-index.md)。

## 用一句话讲清项目

推荐句式：

> 在 `[数据、流量、硬件或权限约束]` 下，为 `[用户问题]` 建立 `[基线]`；实现 `[关键机制]`，并用 `[固定评测与失败切片]` 比较结果；最终以 `[安全、容量或发布门禁]` 限定上线范围。

数字只有在能回答分母、环境、基线和原始结果位置时才写入简历。否则先写机制和验收，不要编造精确提升。

## 五种项目怎样做出深度

### 可诊断企业 RAG

先完成：固定小语料上的 BM25、来源展示和无答案拒答。

做深：加入 dense/rerank、租户 ACL、token budget、引用验证、索引更新和分层错误分析。

适合指标：Recall@k、nDCG、引用正确率、拒答、越权负例、端到端延迟。不要用一个总分掩盖“检索正确但生成错误”。

### 可恢复工具 Agent

先完成：模型只生成 typed proposal，执行层独立校验并调用一个只读工具。

做深：加入审批、幂等 ledger、预算、pending 状态、崩溃恢复和独立 completion verifier。

适合指标：带 verifier 的任务成功率、非法参数拒绝、越权 attempt、重复副作用和未解决 pending。模型说“成功”不计为执行成功。

### 单卡微调与推理

先完成：比较 base Prompt 与一份小规模 LoRA 训练，打印最终 input IDs、labels 和监督 token 数。

做深：加入数据切分、rank/target-module 消融、held-out 评测、adapter 重载、量化和目标 GPU 显存记录。

适合指标：任务指标、格式率、通用回归、峰值显存、训练时间和服务吞吐。Loss 下降不是最终质量指标。

### 单卡推理服务

先完成：固定模型、采样配置和请求，记录非流式与流式输出。

做深：区分排队、prefill 和 decode，加入容量上限、取消、过载、prefix cache 和质量回归。

适合指标：offered/dispatch TTFT、TPOT、吞吐、峰值显存和全部请求 outcome。一次延迟不能代表容量。

### 模型评测平台

先完成：固定 case ID、baseline/candidate 输出和一个可重算指标。

做深：加入错误切片、配对比较、judge 校准、人工复核、发布门禁和历史追踪。

适合指标：effect size、区间、切片回归、人工一致性和门禁结果。统计显著不等于业务重要。

## 证据怎样组织

让读者从简历数字逐层下钻：

```text
resume bullet
  -> 项目 README 的结论与边界
  -> summary report
  -> per-case / per-request result
  -> data / workload manifest
  -> code、config 与模型版本
```

作品集首页保持简洁。精确 hash、fixture 数字、完整测试矩阵和内部协议放在 evidence 页面；本仓库自身的精确项目表述保留在[作品集 claim 证据台账](../evidence/resume-claims.md)，不作为第一次阅读内容。

## README 推荐结构

1. 问题和使用场景。
2. 五分钟最小运行。
3. 架构图与信任边界。
4. 基线、实验变量和结果。
5. 三个最有代表性的失败样例。
6. 复现环境、已知限制和下一步。

截图用于展示，机器可读结果用于复核。敏感数据使用脱敏或合成样例，并说明它与真实数据的差异。

## 常见扣分项

- 把框架名当作核心贡献。
- 只报最好结果，不提供基线和失败样例。
- 在测试集上反复调参。
- 把 CPU demo 描述成 GPU 或生产性能。
- 写准确率却说不清标签、样本量和分母。
- 把 JSON 可解析、模型完成文本或文件 hash 当作业务正确性。
- 无法区分自己的贡献、框架默认行为和团队已有能力。

## 面试前自查

随机选择简历中的一个数字，确认自己能在五分钟内找到它的数据、配置、原始结果和最差样例。然后回答：如果重做，最先增加哪个反例或控制变量？

能回答并展示证据，项目才真正属于你；不能回答时，删掉数字或补做实验。
