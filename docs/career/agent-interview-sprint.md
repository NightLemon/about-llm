# 14 天 Agent / LLM 面试冲刺

<!-- learning-contract -->

**适合读者**：已有 Python 与基础 Transformer 知识，想把 RAG、Agent、训练和评测串成可解释项目的开发者。  
**先修**：[岗位路线](roadmap.md)、[核心面试题](interview-questions.md)和[项目索引](../practice/project-index.md)。  
**首次阅读路径**：先做下面的先修诊断，再按每天一张卡执行；最后三天减少新输入，转向综合演练。  
**完成信号**：能脱稿解释当天机制，留下命令输出或手算记录，并能回答当天追问。  
**卡住时**：回到相应项目页的“Run”与失败说明，记录缺的前提后重跑最小样例。

这份安排把本仓库的机制学习接到一个可复查的 Travel CLI。个人学习证据由自己执行产生：读懂、
跑通、解释失败和独立修改分别记录。每天的阅读是为了完成一个具体动作，读完页面不是当天的终点。

每天按 12 小时切块：4 小时精读、4 小时实作、2 小时面试表达、2 小时复习。
第 12–14 天减少新输入，把相应时间转给已有材料的综合演练；第 11 天的前沿内容只选目标 JD 真正相关的部分。

## 先做 40 分钟诊断

先关掉参考答案，用 20 分钟口述或手写，再用 20 分钟核对。每题记录“能独立解释 / 需要提示 / 尚不能解释”，
这只是自评，不自动代表项目能力。

| 诊断题 | 核对要点 | 缺口的最短回补路径 |
|---|---|---|
| 输入 `[BOS,A,B,EOS]`，训练时每个位置预测谁？ | 常见目标为 A、B、EOS；确认模型内是否已做 shift，不能再错一位。因果 mask 控制可见范围，loss mask 控制计分位置。 | [预训练](../training/pretraining.md)的四 token 算例，自己打印一次 labels |
| 模型返回合法 JSON，为什么仍可能不能执行？ | 结构正确后仍需核对可信身份、工具白名单、参数业务范围与当前授权；返回的总价也需要重算。 | [Agent runtime](../applications/agent-runtime.md)，构造一个合法 JSON 但非法业务参数 |
| top-3 找到两份金标中的一份，Recall 是多少？ | 若按两份金标文档集合计数，则 Recall@3=1/2；Hit@3=1。单命中不能声称证据已齐全。 | [检索](../applications/rag-retrieval.md)，用两条问题写出分子、分母 |
| 下游超时，是否立即用新请求 ID 重试？ | 判断是否有副作用；只读查询可以在预算内重试，写操作需考虑远端已执行但响应丢失、幂等协议与对账。 | [Agent runtime](../applications/agent-runtime.md)，比较只读天气与假设的预订写入 |
| 同样 20 例，成功数变多是否证明改进？ | 核对输入、分母、预算、数据/模型版本及成功定义，保留合法拒绝和失败；脚本模型的改进不能外推真实模型。 | [Agent evaluation](../quality/agent-evaluation.md)，逐例配对而非只比较总数 |

诊断失败时先回补对应机制，不先增加框架。Python 数据结构、函数异常和 JSON 解析仍不熟练时，
先独立完成输入校验，再接模型 API。目标岗位若要求训练或 Infra，再使用专项；应用主线不以先跑通 GPU 训练为前提。

| 11 | 按目标 JD 选读训练、LoRA 或 PPO；为 Travel 写系统取舍。 | 为什么此处不用更复杂架构？保存对照。 |

| 13 | 整理考前材料、简历证据和行为故事；完成模拟 4。 | 哪项结论只来自 fixture？保存限制说明。 |

每晚复习时把错误分成概念、实现、证据三类。概念错回精读页；实现错缩小到
项目的最小命令；证据错补充版本、输入、输出和不能外推的范围。连续两天答不出同一
追问时，暂停新增主题，先手写一个反例并复跑相关固定样例。

## 三张贯穿任务卡

**卡 A：从看懂到独立修改（第 1–4 天）。** 在本地 Travel 项目中先解释一个成功输入和一个非法输入。
关闭参考实现，自己写输入校验或工具 dispatch 的小版本，再增加“整数位置传入布尔值”和“未知工具名”两个反例。
验收看非法输入是否在执行前被拒绝、是否保留明确诊断；不能只展示一条成功行程。代码若由 AI 提供，必须能解释每条
拒绝分支，并在不看答案时修改一个边界条件。对应材料是[核心面试题](interview-questions.md)与 runtime 页。

**卡 B：让证据参与判断（第 5–8 天）。** 为一次行程画出请求、资料版本、候选、最终检查之间的关系。
改变一个引用日期、必选景点或总价，预测哪一步应失败，再运行核对。URL/ID 相符只能证明引用绑定；真实营业时间与
价格是否被资料支持，需要另查证据。Travel 的人工价格和交通假设必须继续标明。把结果接到
[Evaluation Gate](../practice/projects/evaluation-gate.md)，解释为什么“模型说完成”不能代替最终检查。

**卡 C：把实验讲成可以追问的项目（第 9–14 天）。** 固定案例、模型模式、预算上限和代码身份，比较 workflow 与
agent 的逐例结果。消融只移除一条反馈通道，保留最终 gate；分别报告合法输出、预期结果匹配、失败原因和实际用量。
检查结论究竟由 fixture、真实天气还是模型调用支持。随后用两分钟讲需求、选择、一个真实失败及修正，并让练习伙伴
临时改变条件，例如“只能一次模型调用”或“天气超时”。完成信号是能解释取舍，且证据与口述一致。
