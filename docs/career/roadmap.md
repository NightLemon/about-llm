你是一名后端工程师，看到一份 “LLM Engineer” 职位描述：

```text
负责企业知识助手的研发与优化；
熟悉 RAG、Agent、vLLM、LangChain，了解 PEFT；
保障系统稳定性和回答质量。
```

如果按关键词学习，几乎整套 LLM 技术栈都要补。更有用的第一步是问清楚：知识助手答错时，
这个岗位先查 retriever、Prompt 还是训练数据？高峰期出现 `504` 时，是否由它承担 on-call？
Agent 重复发出业务操作时，谁负责状态机和恢复？

**本页用六步走完这一次决策**，每一步只在需要时引入一个工具：

```text
1 读懂这份 JD  → 2 判断哪种失败归我  → 3 给自己的证据定级
                                        ↓
6 准备被追问   ← 5 把结果写成 bullet ← 4 补两个能推翻自己的实验
```

六步走完后，末尾的[换一条路线](#route-reference)和[参考资料](#reference)供你切换目标岗位时查阅。
第一次阅读**不需要**看那两节。

## 我们的主角 { #worked-example }

后面六步都围绕同一个人展开，这样每个工具都能立刻用在同一份材料上。

> **背景**：三年后端开发。写过 API、数据库和队列，也处理过接口超时；
> 会调用模型 API，但没有系统做过检索评测、GPU 性能分析或模型训练。

他的目标就是开头那份 JD。如果你的背景不同，[从已有背景迁移](#background-transfer)
给出了另外五种起点，但**六步的顺序完全一样**。

## 第一步：读懂这份 JD { #read-a-jd }

先把营销名词删掉，只抽取五类信息：

| 信息 | 从 JD 找什么 | 应形成的问题 |
|---|---|---|
| 动词 | 研究、训练、构建、部署、优化、运营、评测、治理 | 日常主要是在提出方法、写系统还是承担服务？ |
| 对象 | 数据、模型、retriever、runtime、Agent、平台、客户方案 | 主要 artifact 和上下游是谁？ |
| 规模 | 单卡/集群、QPS、数据量、租户、区域、端侧 | 哪些容量/分布式能力是真的必要？ |
| 生命周期 | prototype、上线、on-call、迭代、事故、合规 | 是否需要 O 级证据？ |
| 评价 | 质量、收入、SLO、GPU 利用率、安全、交付速度 | 团队怎样判断工作成功？ |

**就地用在开头那份 JD 上**，逐句翻译：

| JD 原文 | 它可能对应的日常工作 | 他现在能拿出的证据 | 还要向团队确认什么 |
|---|---|---|---|
| 负责企业知识助手的研发与优化 | 接入文档、检索、生成、权限和业务 API | 后端服务、数据流、故障处理 | 主要优化回答质量，还是负责整套线上服务？ |
| 熟悉 RAG、Agent、vLLM、LangChain，了解 PEFT | 这些是候选工具，不一定都是主要职责 | 模型 API 和后端框架经验 | 哪个组件由本岗位维护？需要训练或管理 GPU 吗？ |
| 保障系统稳定性和回答质量 | 既要处理 `504`，也要解释错误答案来自哪一层 | 可观测、回滚和接口测试 | 是否承担 on-call？回答质量用什么 case 和指标判断？ |

注意第二行：**JD 里的技术栈是约束，不是完整能力定义**。使用过某个框架，
但说不清输入输出、失败模式和替代方案，证据仍然很弱。反过来，如果你用另一个框架
解决过同层问题，并保存了基准结果和迁移分析，这可以作为相邻证据向面试官解释。

### 分清 must-have 与 nice-to-have

不要只数关键词命中率。优先判断：

1. 是否具备岗位主要失败责任对应的基础能力；
2. 是否有一项可以深挖到原始输出和运行记录的主证据；
3. 缺失技术是同层工具迁移，还是缺少整个能力域；
4. 对地域、许可、学历、工作授权或 on-call 等硬条件是否满足；
5. 能否诚实解释未做过的规模和目标环境。

对我们这位候选人：`vLLM` 和 `PEFT` 属于第 3 条里的"缺少整个能力域"，
而 `LangChain` 只是同层工具迁移。**这两者不该被同等对待**——
一种工具 API 通常可以在短期内补齐，实验设计和端到端负责经验需要更长时间积累。

## 第二步：判断哪种失败会落到我桌上 { #failure-ownership }

岗位名称提供的信号很弱，责任边界更稳定。“LLM Engineer” 可能负责 API 后端、
检索算法、训练、推理平台或客户交付；“算法工程师” 也可能主要维护数据和评测。

仍以企业知识助手为例，同一个产品会产生七类完全不同的失败：

| 线上现象 | 第一个需要回答的问题 | 更接近的责任域 |
|---|---|---|
| 答案引用了错误文档 | gold 文档没召回、被重排丢掉，还是生成器误用证据？ | RAG / 搜索算法 |
| 输出字段错误或接口超时 | Prompt、状态、API、依赖和降级哪一层先偏离？ | **LLM 应用 / 后端** |
| 同一退款被请求两次 | 审批、幂等、pending 与 verifier 怎样恢复？ | **Agent / 平台** |
| 微调后中文能力退化 | 数据 mixture、loss、checkpoint 或评测切片哪里变化？ | 模型 / 训练算法 |
| 高峰期大量 `504` | client queue、admission、KV 还是 decode 饱和？ | 推理 / 系统 |
| 发布 gate 通过但用户变差 | case、标注、指标或统计口径遗漏了什么？ | 评测 / 数据 |
| 越权文档进入 Prompt | ACL、缓存、tool policy 或审计链在哪一层失守？ | 安全 / 治理平台 |

一份工作的日常，往往就是反复处理其中一两类失败。与招聘方沟通时继续追问：

- 团队最终交付的是研究结果、线上服务，还是某项业务指标？
- 上游输入由谁拥有，输出交给谁？
- 是否负责线上 SLO、数据、训练、GPU、权限或发布？
- 工作停留在 prototype，还是覆盖运行、评测、回滚与事件处理？

**我们这位候选人的判断**（上表已加粗他选中的两行）：

- **主路线选 LLM 应用与 RAG**：已有后端能力可以直接支撑 API、权限、状态和故障处理；
- **相邻路线选 Agent 平台**：队列、幂等和恢复经验可以迁移到工具调用；
- **暂不声称模型训练或推理优化能力**：目前没有数据实验、checkpoint 或 GPU 测量证据。

他不应同时转向训练、推理内核和 Agent 研究。
其余五条路线的完整责任画像见[换一条路线](#route-reference)——
**现在不需要读它**，选定一条之后再回来对照。

## 第三步：给自己的证据定级 { #capability-levels }

选定路线后，下一个问题是"我现在算什么水平"。本页用四级证据描述能力，
不按工作年限或职称划线：

| 级别 | 能回答什么 | 证据 |
|---|---|---|
| K — Know | 机制是什么、适用边界在哪里 | 能推导/解释并指出反例 |
| I — Implement | 能否从输入到输出实现最小闭环 | 代码、单元测试、固定样例 |
| V — Validate | 怎样证明实现和改动有效 | baseline、逐 case 结果、消融、统计、失败测试 |
| O — Own | 出现漂移、过载、越权或事故时怎样处置 | SLO、监控、runbook、回滚、权限与事件证据 |

**立刻用在他身上。** 把 RAG 这一项拆成四级，逐级问"我做过吗"：

| 级别 | 在 RAG 上意味着什么 | 他现在的状态 |
|---|---|---|
| K | 能解释 BM25 和重排器分别解决什么问题，也知道反例 | ✅ 读过、能讲 |
| I | 从文档摄取到带引用回答，跑通一条最小链路 | ⚠️ 调用过 API，没有自己实现过 |
| V | 固定相同 case，对比基线和新方案；用消融与留出数据说明改动来自哪里 | ❌ **缺口在这里** |
| O | 为服务定义 SLO 和权限边界，并实际处理发布、回滚和事故 | ❌ |

这四级描述的是**证据覆盖到哪里**，不会随工作年限或职称自动升级。
他的后端经验能让他在"Python、测试、可观测"上直接到 V 甚至 O，
但在 RAG 这条主路线上**卡在 I 和 V 之间**——这就是第四步要补的东西。

同样的定级方法可以套到其他能力域上；完整的七岗位 × 十能力对照表在
[能力矩阵](#capability-matrix)，同样属于查阅内容。

## 第四步：补两个能推翻自己的实验 { #next-experiments }

缺口定位在 V 级，那么下一步不是"再读一本书"，而是**做两个可能证明自己不行的实验**。
挑选标准是：如果做不出来，就说明这条路线不该写进简历。

1. 在[可诊断 RAG](../practice/projects/rag-foundations.md)中固定一组问题，
   分别观察检索、重排、引用和权限过滤。
   **如果无法解释一条错误答案来自哪一层，说明 RAG 还没有学到能面试的深度。**
2. 在 [Safe Agent](../practice/projects/safe-agent.md)中运行一次退款任务，
   解释审批、幂等和超时对账。
   **如果只能讲 Prompt，无法说明重复退款怎样被阻止，就不应把 Agent 平台列为强项。**

注意这两个实验分别对应第二步选中的**主路线**和**相邻路线**，
而不是平均覆盖七条路线。四处各做一个浅 demo 会削弱项目深挖。

完成后，作品集就有了可信组合——**一个主项目 + 一个相邻项目 + 一项底层实现**：

- **主项目**：可诊断 RAG，证明他能把模糊需求变成系统和发布决定；
- **相邻项目**：Safe Agent，证明他理解上下游；
- **底层实现**：[Transformers Basics](../practice/projects/transformers-basics.md)，
  证明他不是只会调用框架，理解模型接口下面的分词、注意力和生成协议。

这已经形成一条清楚的后端转型路线，不需要再做四个换壳聊天机器人。
三者可以共享代码和数据，但**必须避免把同一次实验包装成三份独立证据**。

其他路线的推荐组合见[作品集组合参考](#portfolio-reference)。

## 第五步：把结果写成可审计的 bullet { #evidence-levels }

实验跑完了，现在的问题是"我能把它写成什么"。先给证据本身定级——
注意这是**证据的五级（L0–L4）**，与第三步**能力的四级（K/I/V/O）**是两套不同的尺子：

- L0：文档；
- L1：最小实现；
- L2：可复现实验；
- L3：工程样例；
- L4：生产设计。

到 L4 时，项目已经讨论容量、安全、监控、回滚和成本。真实生产流量、组织流程和可用性，
仍要由实际运行记录证明。

**我们这位候选人的两个实验落在 L2**（可复现实验，CPU 本地固定 case）。
对照下表，这决定了他能写什么、不能写什么：

| 当前证据 | 可以写 | 不应写 |
|---|---|---|
| CPU 确定性样例 | 实现并验证公式/状态机/错误路径 | GPU 加速、生产吞吐 |
| **自编离线样例** | **在固定 N 条回放上得到某结果** | **真实用户整体提升** |
| 目标 checkpoint 单点运行 | 在固定 revision/环境/输入下执行 | 模型总体质量、跨硬件兼容 |
| loopback HTTP integration | 真实本机进程/TCP/HTTP 路径 | 公网、TLS、IAM、多区域可用 |
| 生产设计与故障演练 | 设计/演练某项回滚或控制 | 未实际承担的 SLA、事故或用户规模 |

一个可审计 bullet 可以写成：

> 在 `[数据/流量/硬件/权限约束]` 下，设计并实现 `[关键机制]`；相对 `[基线]`，在 `[固定 workload 与切片]` 上将 `[指标]` 从 A 改为 B，并以 `[安全/统计/回滚 gate]` 限定发布；未覆盖 `[目标环境边界]`。

其中 A/B 只能替换为实际结果。不要为了句子短而删除分母、baseline 或环境；
可以把完整证据放在项目 README/report，在简历保留可下钻链接。

数字反向审计链：

```text
resume bullet
  -> summary report
  -> per-case/per-request result
  -> workload/data manifest
  -> code/config/model revision
  -> raw failure examples
```

链路断在任一层，就不能把数字写成已验证事实。
无密钥 SHA-256 只能帮助发现漂移，不认证执行者、时间或来源。

同一段经历面向不同 JD 怎样改写，见[简历项目与证据包](resume-projects.md)。

## 第六步：准备被追问 { #interview-prep }

简历写完，最后一步是预演面试官会从哪里下钻。

| 环节 | 所有路线共同要求 | 路线差异 |
|---|---|---|
| 编码 | 正确性、边界、测试、复杂度、可读性 | 算法偏张量/统计，系统偏并发/缓存，应用偏 API/data |
| 基础机制 | Transformer、tokenizer、generation、训练与评测边界 | 深度按岗位主要对象增加 |
| 项目深挖 | 数据、baseline、指标、失败、取舍、本人贡献 | 必须能打开 artifact 或重建关键数字 |
| 实验设计 | 假设、控制变量、切片、不确定性、停止条件 | 算法/评测权重更高，但任何路线都不能缺失 |
| 系统设计 | 需求量化、数据流/控制流、容量、安全、降级 | 应用/Agent/推理强调不同瓶颈 |
| 故障排查 | 从现象到分层假设、最小观测、止损、复盘 | RAG 召回、训练 NaN、OOM、尾延迟、重复 effect 等 |
| 行为/协作 | 决策、冲突、失败、ownership、跨团队沟通 | 只讲成功故事无法证明事故处理能力 |

### 项目深挖的六层回答 { #project-deep-dive }

1. **问题**：用户/系统目标和硬约束是什么？
2. **基线**：为什么选择它，成功定义是什么？
3. **机制**：你改变了哪一层，哪些层保持固定？
4. **证据**：case、指标、区间、切片和原始失败在哪里？
5. **取舍**：质量、风险、延迟、成本和复杂度怎样变化？
6. **边界**：当前证据不能支持什么，下一项最可能推翻结论的实验是什么？

回答“我们用了某框架所以效果更好”会在第二、三和四层同时断裂。
这也是第四步那两个实验的价值——它们直接产出第 4、6 层的材料。

### 故障题的回答顺序 { #incident-order }

先止损，再分层，再观测，最后改动：

```text
影响范围/安全风险
-> rollback、限流、禁用副作用或降级
-> input/data/model/runtime/system 分层假设
-> 最小日志、trace、metric、replay
-> 一次只改变一个主要变量
-> 回归集与发布 gate
-> postmortem 和长期预防
```

不要一上来“换更大模型”或“调 Prompt”。

## 六步小结

这位候选人走完六步后得到的，不是一张技能清单，而是一条可以被追问的轨迹：

| 步骤 | 他的产出 |
|---|---|
| 1 读 JD | 三个必须向团队确认的问题 |
| 2 判断失败归属 | 主路线 = 应用/RAG，相邻 = Agent 平台，明确放弃训练与推理优化 |
| 3 证据定级 | RAG 卡在 I 与 V 之间 |
| 4 补实验 | 可诊断 RAG（主）+ Safe Agent（相邻）+ Transformers Basics（底层） |
| 5 写 bullet | L2 级措辞，带反向审计链，不写"真实用户提升" |
| 6 准备追问 | 六层深挖 + 故障排查顺序，材料来自第 4 步 |

**如果你换一条路线，六步顺序不变，只是第 2 步选中的行、
第 3 步定级的能力域和第 4 步的实验换一组。** 下面两节就是用来做这个替换的。

## 七类岗位责任画像

它不是招聘市场占比，也不是统一职级标准；小团队的一个岗位可能横跨两三行。

| 路线 | 主要交付物 | 首先负责的失败 | 核心能力 | 最强作品集信号 |
|---|---|---|---|---|
| LLM 应用/后端 | API 产品、RAG/Agent workflow、业务集成 | 答案错误、接口失败、权限/成本/延迟失控 | Python/后端、Prompt、RAG、Agent、云 API、测试与可观测 | 有 ACL、引用、typed state、预算、故障注入和逐 case 评测的服务 |
| RAG/搜索算法 | ingestion、索引、retriever/reranker、context | 召回、排序、过滤、packing 或引用失败 | IR、embedding、学习排序、数据、检索评测、在线服务 | 分层 retrieval→rerank→answer 评测、消融、切片和索引更新/删除 |
| Agent/平台 | tool/runtime、状态、审批、恢复、互操作 | 越权、重复 effect、循环、pending、跨系统不一致 | 状态机、schema、IAM、幂等、队列/事务、MCP/A2A、verifier | proposal/execution 分离、typed approval、崩溃恢复、outbox 与安全 trace |
| 模型/训练算法 | 数据配方、SFT/PEFT、RM/DPO/PPO、checkpoint | loss/梯度异常、泄漏、过拟合、能力/安全回归 | Transformer、PyTorch/JAX、优化、数据、分布式、实验设计 | 数据门禁、训练恢复、baseline/消融、held-out 与多切片回归 |
| 推理/系统 | runtime、serving、kernel、调度、容量 | OOM、吞吐不足、尾延迟、取消/抢占/缓存错误 | GPU/内存、KV、量化、batching、并行、profiling、网络服务 | 固定 offered-load 下的 TTFT/TPOT/吞吐、显存账本和瓶颈归因 |
| 评测/数据 | case、标注、benchmark、统计、发布 gate | 指标无效、标注偏差、污染、切片退化、错误发布 | sampling、taxonomy、统计、judge 校准、数据治理、实验平台 | 可复算 case/result/manifest、人工 judgment、区间、切片和门禁 |
| 安全/治理平台 | policy、红队、审计、模型/系统卡、事件流程 | 注入、泄漏、滥用、越权、供应链与证据断裂 | 威胁建模、IAM、隐私、安全测试、治理流程、跨团队沟通 | 攻击路径、模型外控制、可重放证据、exception/incident/retirement 闭环 |

### 应用工程与算法工程怎样区分

两者都可能写 RAG、训练脚本和评测。差别更常出现在主要优化对象：

- 应用工程把模型作为不稳定依赖，优化端到端任务、状态、接口、可靠性和成本；
- 算法工程把数据、目标函数、模型行为和实验作为主要对象，优化可归因的质量与泛化；
- 搜索算法位于两者之间，既要做 ranking/数据实验，也要承担索引和在线检索约束；
- 平台/系统岗位把可复现执行、容量、隔离和故障恢复作为主要对象。

LangChain、Transformers 或 vLLM 都可能出现在多条路线中。真正区分岗位的是：
哪些性质必须始终成立，以及失败发生时需要你作出什么决定。

## 从已有背景迁移 { #background-transfer }

本页主角是后端工程师。如果你的起点不同，先复用已有强项，再补相邻的 LLM 特有边界；
六步流程本身不变。

### 后端/全栈工程师

优先考虑 LLM 应用、Agent 平台或评测平台。API、数据库、队列、可观测和运维经验都可以直接复用。
你需要补的是模型特有边界：分词器与对话模板怎样改变输入，非确定生成怎样测试，以及 RAG 如何分层评测。
作品集还应展示权限和发布门禁，让成熟后端能力真正支撑模型功能。

### 搜索、推荐或数据工程师

优先考虑 RAG 搜索、评测数据或训练数据。检索排序、特征管道、A/B 实验和指标设计都是现成优势。
下一步要理解检索结果怎样装入模型上下文，生成回答是否忠于证据，以及模型评审器在哪些 case 上不可靠。
多租户权限与 token 成本则把离线算法连接到真实服务。

### 传统 ML/深度学习工程师

优先考虑模型训练、RAG 算法或评测。训练、优化和实验设计可以继续复用，但公开基准只是起点。
还要补上对话模板如何形成训练输入、工具和 RAG 系统怎样改变模型行为，以及目标服务有哪些延迟和容量约束。
数据来源、模型版本和真实工作负载也要进入实验记录。

### 系统、HPC、编译器或 SRE 工程师

优先考虑推理系统、训练平台或 Agent 平台。性能分析、并行、内存、调度和可靠性是直接优势。
需要补足 Transformer 与 KV cache 的状态变化，并理解生成质量和量化回归怎样约束性能优化。
任何吞吐提升都要绑定模型版本，并通过质量门禁后再比较。

### 安全、隐私或治理工程师

优先考虑 AI 安全平台、Agent 或 RAG 控制面，以及评测治理。威胁建模、身份权限、审计和事故响应能力可以直接复用。
模型带来的新问题包括输出不确定、提示注入、候选工具与真实动作混淆，以及训练或检索数据污染。

先把每种风险写成可以运行的测试样例。模型是否拒答只是观察信号，真正的边界仍由权限系统和控制面实现。

### 研究生或研究背景

优先路线取决于能否把假设转成工程证据。论文复现应补环境、数据、代码质量、失败测试、成本与部署边界；单个 best seed 或作者 benchmark 不能替代可复算实验和软件交付。

# 参考资料 { #reference }

## 如何判断职级与 ownership { #ownership-levels }

职级不能仅由年限、模型规模或论文数量推断。可以用责任范围自查：

- **在明确问题内交付**：能实现、测试并解释一个模块；
- **独立闭环**：能澄清需求、选 baseline、验证、上线/交付并处理常见故障；
- **跨系统 ownership**：能定义接口/SLO、协调上下游、管理迁移和高风险失败；
- **组织级杠杆**：能建立平台、标准、评测或决策机制，让多个团队减少重复风险。

这些不是统一晋升标准。面试时用实际决策和结果说明范围，不要自封“架构师”或把团队成果全部写成个人贡献。

注意这四级描述的是**责任范围**，与[第三步的 K/I/V/O 能力四级](#capability-levels)
是两套独立的尺子：能力四级说的是"你的证据覆盖到哪里"，本节说的是"你负责多大的面"。

## 选择团队时也要做反向评估 { #reverse-evaluation }

岗位是否值得选择不只看模型名称。可以询问：

- 团队拥有的是 demo、内部平台还是有 SLO 的产品？
- 是否能访问失败样本、用户反馈、数据 lineage 和真实评测？
- 模型/数据/GPU/API 预算如何分配，谁决定发布？
- 是否有权限、安全、隐私、合规和 incident owner？
- 工作主要是短期客户定制、长期平台还是研究探索？
- 失败时能否回滚，是否需要 on-call，如何做复盘？
- 个人能否拥有端到端结果，还是只维护不可观测的中间环节？

研究岗位可以用可复现实验和被采用的方法证明价值，平台岗位可以用内部用户、迁移结果和故障恢复记录证明价值。
无论是否直接承载生产流量，都要问团队怎样定义成功、是否保留原始结果，以及失败能否被及时发现。

## 常见准备误区

### 同时准备所有路线

四处各做一个浅 demo 会削弱项目深挖。先选主要失败责任，再补一条相邻能力；通用底座仍包括 Python、Transformer、测试、实验设计和系统边界。

### 用课程完成度代替能力证据

看完章节、拿到证书或运行 notebook 不等于能独立验证和负责。把学习产出转换为代码、测试、报告、失败样本和 decision record。

### 只展示最好结果 { #only-best-results }

面试官更关心失败如何分类、为什么归因、怎样回滚。保存负结果、被淘汰方案和阈值选择，不要只放最好的一次 seed。

### 夸大证据等级

CPU 样例、loopback、作者自编数据、schema 校验和模型拒答各自只覆盖一层。GPU 吞吐、公网可靠性、真实用户效果、
业务正确性和权限安全都需要对应环境中的结果。

### 把框架熟练度当核心壁垒

框架会变，稳定能力是识别输入输出契约、构造正确基线、定位失败、验证修改并控制发布。熟练使用框架仍有价值，但必须能解释它替你做了什么。

## 求职决策记录模板

为每个目标岗位维护一页，而不是维护一个无限增长的“LLM 技能清单”。
模板的六个区块与本页六步一一对应：

```markdown
# Role decision record

## Target                          <- 第一步、第二步
- company/team/JD snapshot:
- primary failure ownership:
- main deliverables and scale:

## Evidence map                    <- 第三步
- strongest K/I/V/O evidence:
- flagship project and artifact links:
- adjacent evidence:

## Gaps                            <- 第四步
- hard missing domain:
- tool-level migration:
- claim I must not make:
- smallest falsifiable next experiment:

## Interview                       <- 第五步、第六步
- likely coding/mechanism/experiment/system loops:
- three project decisions to defend:
- two failures and one conflict story:

## Decision
- fit, learning surface and risks:
- questions for the team:
```

这个模板不要求公开公司机密。真实工作证据应脱敏、获得授权，并避免上传客户数据、密钥、内部 Prompt、日志或专有代码。

## 完成检查

- [ ] 用失败责任而不是 title 选择了一条主线。
- [ ] 对一个真实 JD 完成了动词、对象、规模、生命周期和评价拆解。
- [ ] 每个 must-have 都有证据、相邻证据或明确缺口。
- [ ] 有一个主项目能下钻到逐 case/逐请求 artifact。
- [ ] 能解释当前证据的 L0–L4 等级和不能外推的边界。
- [ ] 简历每个数字都能反向追到 workload、配置、代码 revision 和失败样本。
- [ ] 能完成机制、实验、系统设计、故障和项目深挖五类追问。
- [ ] 没有把自编样例、CPU 本地运行或生产设计写成真实线上结果。
- [ ] 准备了对团队的数据、预算、ownership、发布和事件流程问题。

完成这些检查不保证录用；它证明的是你的求职材料内部一致、可核验，并与目标岗位责任相匹配。
