假设你在做一个账号安全助手。用户问：“有人让我转发登录验证码，我该怎么办？”两份候选回答是：

> **A**：不要转发验证码。请通过你自己确认的官方渠道核实对方身份。
>
> **B**：按对方说的发过去就好。

团队认为 A 更合适，因为它给出了安全、可执行的下一步。现在的问题是：**怎样把这次判断变成模型的学习信号？**
你可以直接示范 A，也可以只记录“A 优于 B”，还可以让模型继续生成新回答，再评价它们。
这些选择对应不同的训练方法。

## 先区分四种方法 { #_2 }

### SFT：直接示范怎样回答

监督微调（Supervised Fine-Tuning，SFT）把用户问题与示范回答 A 组成训练样本。
模型逐 token 学习在这个问题后生成 A；较差回答 B 不参与这条示范的损失计算。
想理解哪些位置真正产生损失，可以回到 [SFT 数据闭环](sft-data-pipeline.md)打印最终 labels。

SFT 的信号很直接：这里有一份值得模仿的回答。若示范本身有错，训练也会鼓励模型重复那个错误。

### 奖励模型：学习比较两份回答

奖励模型（Reward Model，RM）读入问题以及 A、B，学习给 A 更高的分数。
在常见的成对偏好训练中，标签告诉它 `score(A) > score(B)`，并没有给出“A 应该值 9 分”的绝对标准。

这一步更新的是打分模型。原来负责回答的语言模型不会仅因打分器学好了就自动改变；还要决定怎样使用这些分数。
例如，让打分器给新回答评分，再把分数用于后面的 PPO 训练。

### DPO：用回答对直接更新生成模型

直接偏好优化（Direct Preference Optimization，DPO）也使用问题和 A、B，但直接更新生成模型。
这里把给定问题后对回答分配概率的模型称为**策略（policy）**。

经典 DPO 还保留一份不更新参数的**参考策略（reference policy）**。训练同时比较当前策略与参考策略对 A、B 的概率，
推动当前策略相对于参考策略更加偏向 A。参考策略提供比较基准，不是另一位负责判断事实的评审。

这样可以用已收集的偏好对训练，不必先训练独立奖励模型。公式、序列概率和系数的作用留到
[DPO 进阶讲解](alignment.md)再展开。偏好标签若偏爱冗长或自信的语气，这条路线也会把偏差学进去。

### PPO：生成新回答，再利用奖励更新策略

近端策略优化（Proximal Policy Optimization，PPO）是强化学习（Reinforcement Learning，RL）中的一种方法。
它让策略实际采样新回答。例如，同一个问题下，模型这次生成 C：“先暂停操作，再从官方应用中确认。”
这次生成过程及其概率等记录构成一条采样轨迹（rollout）。

奖励模型或任务规则给 C 评分；训练程序结合奖励和价值估计，判断这次选择比预期好还是差，形成优势（advantage）信号。
价值估计由价值模型或价值头给出，用于估计后续回报。它可以保存在采样记录中，供这一轮更新使用。

PPO 保留生成这批回答时的旧策略概率，与更新中的策略概率比较，限制一次更新走得过远。
在常见语言模型训练中，还会用相对参考策略的 KL 散度（Kullback–Leibler divergence）约束偏离程度。
旧策略记录这一批回答怎样采样，参考策略提供偏离基准，它们承担不同职责。

因此，PPO 的直接训练对象是**新采样的回答 C 及其反馈**。原来的 A/B 对可以用来训练奖励模型，
但不能直接替代 C 的轨迹、旧策略概率和奖励。

### 把同一组回答放回一张表

| 方法 | 本例主要用什么 | 更新什么 |
|---|---|---|
| SFT | 问题与示范 A | 生成模型，使它更倾向于生成示范 token |
| 奖励模型 | 问题、A、B 和“A 更好”的标签 | 打分模型，使它把 A 排在 B 前面 |
| DPO | 问题、A/B 偏好和冻结参考策略 | 生成模型，使它相对参考策略更偏向 A |
| PPO | 新采样的 C、旧策略概率、奖励与价值估计等轨迹信息 | 生成策略；通常同时训练价值模型或价值头 |

利用人类反馈训练的这一类方法通常称为 RLHF（Reinforcement Learning from Human Feedback）。
“收集人类偏好 → 训练奖励模型 → 用 PPO 更新策略”是一条常见路线。DPO 则可以直接利用偏好对完成策略更新。
开始偏好训练前，通常先通过 SFT 建立可用的指令跟随能力，再比较是否值得增加后续步骤。

## 数据流比算法名字更重要 { #_3 }

回到 A 和 B。只记下“A 赢了”，一个月后很难解释模型为什么学会某种偏好。还需要保存：

- 两份回答对应的原始问题，以及各自由哪一版模型生成；
- 评审依据，例如“保护验证码，并给出安全下一步”，以及谁参与了判断；
- 展示顺序、偏好强度，以及平局、无法判断和评审意见不一致的情况；
- 样本属于训练、验证还是测试集，以及同组问题是否跨了集合。

这些记录帮助你区分“模型学错了”和“我们提供的反馈就有问题”。同样重要的是系统控制：
即使模型学会了 A 的回答方式，读取账号资料和执行操作的权限仍须由应用检查。

## 最小离线审计 { #_4 }

先检查一份偏好数据是否保留了上述信息。从仓库根目录运行：

~~~powershell
python -m about_llm.preference_cli audit --jsonl projects/single-gpu-finetuning/preference.example.jsonl --require-splits train,validation,test --output artifacts/preference-audit.json
~~~

文件里是四条用于检查数据格式的英文固定样例，并非上面的验证码回答对，也没有运行模型训练。
输出中先找三处：

1. `split_counts`：是否有训练、验证、测试三部分；再看同组或重复回答有没有跨集合。
2. `label_counts`：四条里有一条平局（`tie`），它应作为平局保留下来。
3. `preferred_display_position_counts`：被偏好的回答出现在第几个展示位置；这有助于发现位置偏差的线索。

报告还汇总标签强度；各候选由哪一版模型生成，需要回到原始记录的 `generator_revisions` 查看。
字段齐全只说明这些检查能执行；
仍需阅读样本，判断评审标准是否合理、标签是否可信，以及措辞不同的内容是否实际重复。
平局或无效记录可以按训练方法的要求明确筛选，原始记录应保留，不能偷偷改成某一方获胜。

## 怎样选择下一步 { #_5 }

如果只有高质量示范 A，先做 SFT，并用独立问题检查效果。它能建立基本的格式和回答流程。

如果已有稳定的生成模型和可信 A/B 偏好，可以先比较 DPO 与原模型。
若要让模型持续尝试新回答，并能提供可靠奖励、计算预算和安全约束，再评估奖励模型加 PPO 等在线训练路线。
实时事实适合从检索或工具获取；业务权限仍放在系统执行层。

## 分数提高后，还要检查什么 { #_6 }

假如奖励模型把“更长”当成“更安全”，生成模型可能通过增加无关提醒来得高分，关键安全建议却没有改善。
这种利用评分规则缺陷获得高分的现象，称为奖励投机（reward hacking）。

因此，保留没有参与训练的独立问题，同时检查任务是否完成、拒答是否恰当，以及不同人群和场景上的失败。
还可以把 A 缩短、把 B 写得更长，观察打分器是否仍能按内容判断，而不是按篇幅选答案。

## 自测

1. 只有问题和示范 A 时，能直接建立哪一种训练样本？还缺什么才适合做成对偏好训练？
2. 哪一步只训练打分器，哪一步会让生成模型采样新回答 C？为什么旧 A/B 对不能代替 C 的采样记录？
3. 奖励模型给 C 更高分，但 C 没有提醒用户保护验证码。应回查哪项评分依据，怎样设计一个反例？
