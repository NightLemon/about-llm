# 生成与解码

## 从 logits 到文本

模型最后一层对词表输出 logits \(z\in\mathbb{R}^{V}\)。softmax 变成概率：

\[
p_i=\frac{\exp(z_i/\tau)}{\sum_j\exp(z_j/\tau)}
\]

温度 \(\tau\) 小于 1 会让分布更尖锐，大于 1 会更平坦。温度为 0 通常在 API 中表示贪心选择的特殊约定，不应直接代入除法公式。

每次选择 token 后，将其追加到上下文并继续，直到生成 EOS、命中停止序列、达到最大 token 数或外部取消。

## 常见策略

- **Greedy**：每步取概率最高 token。确定、快速，但局部最优不保证整段最好，且可能重复。
- **Temperature sampling**：按缩放后的完整分布采样，控制随机性。
- **Top-k**：只保留概率最高的 k 个 token；固定 k 不适应分布尖锐程度变化。
- **Top-p/nucleus**：保留累计概率至少为 p 的最小集合；候选数动态变化。
- **Min-p/typical sampling**：按相对概率或信息量过滤，部分生成框架支持。
- **Beam search**：保留若干累计分数最好的序列，适合有明确目标的翻译等任务；开放式对话中可能产生安全、重复或平庸文本。

通常先做 logits penalty/约束，再过滤，再归一化采样。不同库的处理顺序可能不同。

## 长度、重复和停止

序列 log probability 是 token log probability 之和，天然偏好短序列；beam search 常用长度归一化。重复惩罚、frequency penalty 和 presence penalty 能减少复读，但可能伤害代码、数字、引用等需要精确重复的内容。

停止字符串可能跨 token 边界；服务端通常在解码文本流中检测。EOS 由模型预测，`max_tokens` 是硬预算。结构化输出不能只依赖“请输出 JSON”，可使用 grammar/JSON Schema 约束解码并在应用层验证。

## 确定性并不绝对

即使 temperature=0，GPU 并行归约、低精度、批调度、模型版本、服务端实现和相同分数的 tie-breaking 都可能带来差异。需要审计级复现时，固定模型哈希、框架、硬件、随机种子、采样器、提示模板和批处理条件，并保留原始 token。

## 约束解码

有限状态机、正则语法或 JSON Schema 可以在每一步屏蔽不合法 token，保证语法有效。但它不能保证字段语义真实、值满足业务规则或工具调用安全。语法校验后仍需类型、范围、引用和权限验证。

## 生成质量的选择

- 事实问答/抽取：低温度、证据约束、多次验证。
- 创意写作：适度提高温度或 top-p，允许多候选再筛选。
- 代码：低到中温度，多样采样配合编译/测试选择。
- 数学推理：生成多个候选、使用验证器或工具，比盲目提高随机性更可靠。
