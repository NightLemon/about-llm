# Tokenization

## 一句话结论

Tokenizer 把原始文本变成有限词表中的整数 id，模型只直接看到这些 id。切分方式影响序列长度、计算成本、多语言表现、数字/代码能力和提示边界，是模型定义的一部分，不能在不适配权重的情况下随意替换。

## 基本流程

典型流程包含规范化、预切分、子词切分、映射 id 和加入特殊 token。并非每个 tokenizer 都执行全部步骤。

例如“unhappiness”可能被切为 `un`、`happi`、`ness`；中文可能按常见汉字、词组或 UTF-8 字节片段切分。token 不是词，也不总对应可见字符。空格、换行和前导空白可能属于 token 的一部分。

## 常见算法

### BPE

从字符或字节开始，反复合并语料中高频相邻对，直到达到词表大小。编码时应用学习到的合并规则。优点是简单高效；缺点是贪心合并不直接优化语言模型目标。

### WordPiece

与 BPE 相似，但合并选择更偏向提高语料似然，常使用特殊前缀表示词内子词。实际实现细节依模型而异。

### Unigram Language Model

从大候选词表出发，迭代移除对语料似然影响较小的子词；编码可用动态规划选择高概率切分，也能进行 subword regularization。

### 字节级与字节回退

以 UTF-8 字节保证任何输入都可表示，不需要 `[UNK]`，但罕见文字可能变成更长序列。很多现代 tokenizer 混合常见子词与字节回退。

## 词表与序列的权衡

词表大：序列通常更短，但输入/输出 Embedding 参数更多，稀有 token 学习不充分。词表小：Embedding 更省，但序列更长，注意力和 KV Cache 成本上升。不同语言的“每字符 token 数”不一致会带来成本与有效上下文不公平。

词表大小为 \(V\)、隐藏维度为 \(d\) 时，Embedding 矩阵有 \(Vd\) 个参数。若输入 Embedding 与输出 head 权重共享，可显著减少参数。

## 特殊 token 与聊天模板

常见特殊 token 表示 BOS、EOS、PAD、UNK，以及 system/user/assistant/tool 等角色边界。聊天 API 最终通常把消息经 chat template 序列化为 token。角色标记、换行或 generation prompt 不匹配训练格式，会明显降低质量或导致模型续写用户文本。

Padding 分左侧和右侧；批量生成时要结合模型类型、位置 id 和框架要求选择。训练 label 常把 padding 与不需要计算损失的 prompt 部分设为 ignore index（常见为 -100，但以实现为准）。

## 安全与失败模式

- 字符看起来相同但 Unicode 码点不同，可能绕过关键词过滤。
- 零宽字符、组合字符和同形异义字会影响匹配。
- 提示末尾的空格或换行可能改变首个生成 token 分布。
- 直接按字符截断可能切断多字节编码或特殊模板；应按 token 预算截断。
- 对数字逐位或不一致切分，可能影响算术与精确复制。

## 实验建议

选择至少三种 tokenizer，比较中文、英文、代码、JSON、数学公式、emoji、罕见姓名的 token 数和切分。记录压缩率（字节/token 或字符/token），检查 decode(encode(text)) 是否无损，并观察前导空格。
