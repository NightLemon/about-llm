# 代码 Agent：从失败证据到最小补丁

<!-- learning-contract -->
<div class="learning-contract" markdown="1">

**学习导航**

- **适合读者**：希望让模型修改真实仓库，而不只是生成代码片段的开发者。
- **先修**：Git、单元测试、静态检查和[Agent 任务主线](agent-task-lifecycle.md)。
- **首次阅读**：任务契约 → 代码上下文 → 失败假设 → 最小 Diff → 工具反馈 → 仓库级评测。
- **完成信号**：能为一次代码修复固定基础版本、失败证据、允许范围、补丁身份和分层验证结果。
- **卡住时**：先只做“固定一个失败测试并生成最小补丁”，暂时不要讨论发布。

</div>

继续总览中的 `refund-duplicate-fix`：退款服务在重试后产生了两笔外部退款。代码 Agent 收到的不是一道独立编程题，
而是一个已经发生在具体仓库、具体版本和外部状态中的故障。

本章的目标也不是让模型“写出一个幂等函数”，而是让一次修复能够被其他人复现、审阅和否决。

## 第一步：把自然语言请求改写为任务契约

“修复重复退款”至少缺少六类信息：

| 字段 | 本例需要回答的问题 |
| --- | --- |
| 基础版本 | 失败发生在哪个不可变 Git 提交？ |
| 失败证据 | 哪条命令、哪个输入和哪个外部状态能复现两次退款？ |
| 预期行为 | 同一笔业务退款重试后应产生几次外部效果？ |
| 允许范围 | 可以修改哪些模块、依赖、迁移和配置？ |
| 验证要求 | 哪些目标测试、回归、安全与性能检查必须通过？ |
| 发布权限 | Agent 只能准备补丁，还是获得了实际放量权限？ |

缺失项会改变修复方案时，Agent 应先提问或把它标成待确认，而不是默默选择一个答案。

对外部副作用还要区分两件事：客户端发送了几次请求，支付服务实际应用了几次退款。即使本地只调用一次，网络重试、
队列重投或恢复流程仍可能让远端收到多次。可靠目标通常需要稳定的业务效果编号、远端幂等契约和结果未知时的对账。

## 第二步：代码上下文不是“找几个相似文件”

行内补全和仓库修复需要不同上下文。纯自回归模型从左到右生成；中间填充（fill-in-the-middle，FIM）还会把光标前缀、
后缀和待补位置按模型约定重新排列。FIM 的特殊 Token 与顺序属于模型契约，必须查对应模板。

仓库修复则要追踪跨文件关系。退款案例可以按下面的顺序检索：

1. 失败测试、错误输出和调用堆栈；
2. 退款 Handler 与幂等键的定义；
3. 所有调用者、接口、Schema 和数据库约束；
4. 相邻测试、重试配置、依赖锁文件和仓库内开发说明；
5. 必要时查看相关提交历史与代码所有者。

文本和路径相似度只适合找入口。符号定义与引用、抽象语法树索引、语言服务器、调用图和最近修改位置，通常更能说明
代码之间的真实关系。

每个上下文片段要保存路径、仓库版本、符号或行范围，以及选择理由。代码变化后，旧行号和旧索引可能失效；缓存键应包含
代码提交和索引版本。

上下文预算优先留给失败证据、当前符号、接口与调用者、测试，最后才是更远的配置和文档。片段尽量保留完整函数、类型或
语法块。在字符串或条件分支中间截断，可能直接改变程序含义。

## 第三步：先写失败假设，再动代码

退款重复提交的第一版假设可以是：

> 每次重试都生成新的幂等键，支付服务因此把它们当成不同退款。

接下来的循环是：

1. 在固定工作目录和环境中复现失败，保存命令、退出码和脱敏输出；
2. 读取仓库说明、实现、调用者和相关测试；
3. 用新证据支持或推翻当前假设；
4. 生成尽量小的 Diff；
5. 先运行格式、静态、类型和目标测试；
6. 再运行更广的回归与安全检查；
7. 审阅实际 Diff、生成文件、迁移和依赖变化。

最小补丁减少了无关修改，但仍可能改错位置、漏掉生成产物或与新提交冲突。应用前要核对基础版本，应用后要重新读取磁盘上
真正形成的 Diff。Agent 不能通过删除测试、放宽断言或扩大权限来换取绿色结果。

## 第四步：把工具输出当成下一条观察

编译器、类型检查器、单元与集成测试、Linter、静态分析器、Fuzzer 和 Benchmark 都会产生新证据。每次执行至少记录：

- 命令、工作目录、环境和超时；
- 输入代码版本与补丁身份；
- 退出码和完整但脱敏的输出；
- 失败来自产品代码、测试基础设施还是资源超时；
- 剩余修复轮数、Token 和执行预算。

测试失败后，Agent 应更新诊断，再决定修改代码、补充上下文还是停止并请求帮助。机械重复同一补丁只会消耗预算。

测试通过也有明确边界：它说明被选中的输入，在当前环境和判断标准下符合预期。它没有覆盖的路径仍然未知，测试实现本身
也可能写错。

## 第五步：不可信代码在受限环境中运行

模型生成的补丁、仓库原有代码和依赖安装脚本都可能执行任意程序。隔离环境至少控制：

| 资源 | 要限制什么 |
| --- | --- |
| 文件系统 | 只挂载必要工作区，输出写入指定目录 |
| 网络 | 默认关闭，按域名和操作临时放行 |
| 进程与设备 | 进程数、系统调用、GPU 和 Docker Socket |
| 计算资源 | CPU、内存、磁盘、时间和输出大小 |
| 凭据 | 不注入云 Metadata Token、生产数据库或无关密钥 |
| 依赖 | 锁定来源、版本与哈希，审查构建钩子和软件物料清单 |

容器只是隔离机制之一。把宿主 Docker Socket 或高权限凭据挂进容器，容器内程序仍可能控制宿主和生产系统。

安全修复还要增加针对原漏洞的回归测试。SQL 使用参数绑定；命令、路径和 HTML 按各自上下文做转义或白名单；授权在服务端
重新检查；密码学使用成熟库。迁移、删除和外部写入需要审批、备份与恢复方案。

同一个模型生成和审查补丁时，两个角色可能共享盲点。关键修改要由独立工具或人复核。

## 第六步：代码评测要走到仓库行为

验证层级逐步增加：

1. 代码能否解析和编译；
2. 类型与静态检查是否通过；
3. 可见和私有单元测试是否通过；
4. 集成与系统行为是否符合预期；
5. 性质测试、模糊测试和变异测试是否暴露判断标准缺口；
6. 安全、性能、兼容性和可维护性是否满足发布要求。

退款修复的关键判断不是“某函数只调用一次”，而是同一业务效果编号在重试、超时和恢复后只产生一次外部退款，
同时不同退款请求不会被错误合并。

仓库级评测要固定基础提交、Issue、环境和测试集合。补丁能否应用、修改范围、依赖变化、回归、安全、时间和成本，
都应分别记录。

公开任务可能已经进入模型训练数据，因此最终选型还需要新鲜或私有任务。

## `pass@k` 回答的是“给多次机会能否至少成功一次”

对同一任务生成 (n) 个候选，其中 (c) 个通过验证器。给 (k) 次机会至少通过一次的常用估计为：

\[
\operatorname{pass@k}=1-
\frac{\binom{n-c}{k}}{\binom{n}{k}},
\qquad 1\le k\le n.
\]

仓库中可以直接运行：

```python
from about_llm.evaluation import pass_at_k

score = pass_at_k(num_samples=10, num_correct=2, k=2)
assert score == 17 / 45
```

这个数描述同一任务有 (k) 次候选机会时，至少一个候选通过当前验证器的概率估计。线上只生成一次时，不能把 `pass@10`
写成单次成功率。报告还要给出 `pass@1`、每题候选数、采样设置、Token 预算和执行成本。

候选高度相关、抽样分布变化或验证器本身有误时，指标解释也会变化。验证器只判断测试是否通过，并不自动识别不可维护实现、
隐藏安全缺陷或训练数据污染。

## 运行仓库中的公式验证

```powershell
python -m pytest tests/test_code_metrics.py -q
```

这组测试核对 `pass_at_k` 的组合公式、输入范围和若干边界情况。它没有运行代码生成模型，也没有证明某个 Agent 能修复大型仓库。

## 自测

1. 为什么“同一个函数只调用一次”不足以证明没有重复退款？
2. 哪些代码关系适合符号索引，哪些场景才适合向量检索？
3. 目标测试通过后，为什么还要重新读取实际 Diff？
4. `pass@10` 为什么不能直接写成单次线上修复成功率？
