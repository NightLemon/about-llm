RAG（Retrieval-Augmented Generation）常被介绍成“先搜索，再让模型回答”。
这句话没有错，却省略了最容易出事故的部分：搜索谁能看的资料、哪些片段真的能回答、
模型有没有忠实使用证据，以及证据不足时为什么没有停下来。

本章从一个内部知识库问题开始：

> 工程师问：RAG 为什么要先做 ACL 权限过滤？

一个可信答案可以是：

> 检索必须先执行租户隔离和 ACL 权限过滤，再进行排序与上下文构建。[S1]

要让这句话可以安全发布，系统不能只“找到一段相似文字”。它必须完成一条证据流水线。

## 先认识这次请求

调用者来自 `tenant-a`，拥有 `engineering` principal。知识库中有四类资料：

| 资料 | 权限 | 与问题的关系 | 请求能否使用 |
|---|---|---|---|
| `rag-security` | `tenant-a / engineering` | 直接说明 ACL 顺序 | 可以 |
| `rag-evaluation` | `tenant-a / public` | 讨论引用与评测 | 可以 |
| `finetuning-basics` | `tenant-a / ml` | 讨论微调 | 不可以 |
| `tenant-b-secret` | `tenant-b` | 故意包含很多相似关键词 | 不可以 |

这里的 `public` 只表示租户内公开，不表示跨租户公开。
请求体也不能自己声明 tenant 或 principal；这些身份必须来自认证层。

## 一条完整的 RAG 流水线

```mermaid
flowchart LR
  Q["问题 + 可信身份"] --> A["授权候选集"]
  A --> R["召回"]
  R --> K["重排"]
  K --> P["上下文组装"]
  P --> G["生成或抽取"]
  G --> C["引用与主张检查"]
  C --> O["发布 / 拒绝 / 澄清"]
```

这七步解决的是不同问题：

| 环节 | 它回答什么 | 典型失败 |
|---|---|---|
| 授权 | 当前调用者允许使用哪些资料？ | 跨租户泄漏、ACL 后移 |
| 召回 | 小候选集是否覆盖所需证据？ | 答案在库中却没找到 |
| 重排 | 哪些候选最值得占用上下文？ | 主题相似段落压过答案段 |
| Packing | 在 token 预算内放入哪些证据？ | 正确片段被截掉或挤掉 |
| 生成 | 怎样把证据变成回答？ | 模型改写错误、依靠参数记忆猜答 |
| 引用 | 每个可验证主张由什么支持？ | 引用不存在、漏引或引用不蕴含主张 |
| 发布决策 | 现在应回答、拒绝还是澄清？ | 有资料时误拒答、无资料时硬猜 |

RAG 的目标不是“总能回答”，而是在给定权限和证据下产生可验证行为。

## 第一步：授权不是检索后的补丁

知识库的可信摄取与索引进程可能有权处理全部文档；在线请求没有。
请求路径必须先确定可见集合，再用这个集合计算查询期统计、分数、缓存键和候选结果。

如果先在全库打分、最后才删除越权结果，仍可能泄漏：

- 隐藏文档改变 IDF、平均长度或归一化分数；
- 越权正文进入 reranker、日志、trace 或模型上下文；
- 缓存把一个主体的结果复用给另一个主体；
- 时间和候选数量暴露隐藏资料是否存在。

仓库的 BM25 基线先得到可见文档索引，再只用它们计算查询期统计与排序。
Reranker 和 context packer 还会再次检查授权，因为不能把上游输出当作永久可信。

## 第二步：召回先追求证据覆盖

召回器把大量可见资料缩小成候选集。它不负责写答案。

- BM25 擅长错误码、产品型号、人名和原词匹配。
- Dense retrieval 擅长语义改写，但可能忽略精确实体和否定。
- Hybrid retrieval 合并 sparse 与 dense 的长处。
- Metadata filter 处理生效时间、产品、区域和文档状态。

本例的 BM25 前三名中，直接答案段排第一；另两段只是相关背景。
这时要问的是“答案段是否进入候选集”，而不是“最终答案看起来好不好”。

Recall@k 衡量 gold evidence 被候选覆盖的比例。它很重要，但高 Recall 仍不保证排序、packing 或回答正确。

## 第三步：重排是在有限预算内重新判断

召回器需要便宜地看很多资料，reranker 可以更慢、更细地比较少量 query–passage pair。
常见结构是：

```text
大量授权文档 -> 100 个召回候选 -> 20 个重排候选 -> 5 个上下文片段
```

本仓库的 recorded-score 教学样例把两个 `rag-security` 片段排到前两位，
把只讨论一般评测的段落降到第三位。它真实验证了授权、绑定和排序控制流，
但分数是人工 fixture，不代表 learned reranker 提高了质量。

## 第四步：上下文不是简单取 top-k

上下文组装需要同时考虑：

- 完整 Prompt 的 token 预算与输出预留；
- 同一来源的重复片段和每来源配额；
- 邻接段落、标题、版本和生效时间；
- 稳定、短小且只指向已授权资料的 source ID；
- 文档中的 Prompt injection 只能被当作数据。

最终上下文可能把第一段映射为 `S1`：

```text
<source id="S1">
检索必须先执行租户隔离和 ACL 权限过滤，再进行排序与上下文构建。
</source>
```

短 ID 由服务端分配。不要让模型自己拼内部 URL，也不要把模型输出的 source ID 当成授权证明。

## 第五步：引用正确至少有四层

“答案后面有 `[S1]`”只通过了最外层格式检查。

| 层 | 要验证什么 |
|---|---|
| Citation validity | `S1` 存在，并且当前调用者有权查看 |
| Citation coverage | 需要证据的主张是否都带引用 |
| Citation correctness | `S1` 的内容是否支持相邻主张 |
| Answer completeness | 是否遗漏必要条件、冲突证据或反例 |

仓库的本地 citation audit 能可靠检查前两类语法问题，不能自动证明语义蕴含。
逐字抽取 baseline 能证明答案 span 来自已打包证据，仍不能证明来源真实或回答完整。

## 第六步：拒答不只发生在零结果时

再看一个追问：

> 引用的 Kubernetes 灾难恢复步骤是什么？

知识库里有“引用”“拒答”等相似词，因此召回器仍返回若干主题相关片段。
但这些片段没有 Kubernetes 灾备步骤。正确行为是：

> 证据不足，无法基于已授权知识库回答。

这说明“检索有结果”和“问题可回答”不是一回事。拒答至少有三种位置：

1. **生成前拒答**：没有任何已授权证据，不调用模型。
2. **证据不足拒答**：有主题相关资料，但无法覆盖问题所需事实。
3. **生成后拒绝发布**：模型输出漏引、引用未知来源或违反输出协议。

它们需要不同的 reason code 和指标。把三者都渲染成一句“我不知道”，会丢失诊断信息。

## 怎样定位一次失败

不要从最终回答倒猜。沿证据链逐层找第一个错误：

| 观察 | 首先检查 |
|---|---|
| Gold 资料根本不在 corpus snapshot | 摄取、版本、删除传播 |
| Gold 资料存在但当前主体不可见 | 标注权限或授权策略 |
| 可见却未进大候选集 | query、BM25/dense、ANN |
| 候选中有、重排后消失 | reranker、截断、候选深度 |
| 重排后有、最终 context 没有 | token budget、去重、来源配额 |
| Context 有、答案没使用 | Prompt、生成器、解码与模型能力 |
| 答案有引用但主张不受支持 | claim–evidence correctness |
| 无答案却发布了事实陈述 | 拒答策略与发布门禁 |

只有保存每一层的输入、输出和 identity，才能完成这种归因。

## 先建立弱而透明的基线

第一次构建时，推荐按下面的顺序增加复杂度：

1. 用少量人工可审阅语料和 BM25 建立召回基线。
2. 加入跨 tenant、ACL blocked 和无答案负例。
3. 用逐字抽取答案验证 packing、短引用和拒答路径。
4. 用固定 qrels 分别评价召回、重排、上下文和回答。
5. 再接 Embedding、ANN、learned reranker 和生成模型。
6. 最后在目标硬件、真实流量和真实权限服务上验证。

弱基线的价值不是质量高，而是失败原因可见。模型接入后，保留它作为回归 oracle。

## 自测

1. 为什么跨租户文档即使最终没返回，也不应参与查询期 BM25 统计？
2. Recall@10 很高而答案仍错误，至少列出三个下游原因。
3. `[S1]` 是已授权 source ID，为什么仍不能说明相邻主张正确？
4. 有三个主题相关结果时，系统为什么仍可能需要拒答？
5. 生成前 abstain 与生成后 reject 应不应该共用同一个指标？为什么？
