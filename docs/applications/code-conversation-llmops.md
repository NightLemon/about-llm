用户在长对话中提出：

> 退款服务在重试后提交了两次，请修复并帮我发布。

这句话把三个任务压在了一起：

1. **代码修复**：在哪个仓库版本上复现失败，哪个最小补丁改变了幂等行为？
2. **暂停与恢复**：任务中断后，系统怎样知道测试是否运行、发布是否获批、远端退款是否仍然未知？
3. **发布与运维**：线上运行的是哪份代码、模型、Prompt、工具策略和索引，失败后要回滚什么？

只让模型生成一段补丁，最多完成了第一项的一部分。本章用示意任务 `refund-duplicate-fix` 连接三段工作，
再把每段交给一篇可以独立学习的专题章节。

这个任务不是仓库录制的真实退款事故。仓库能运行的是 `pass@k`、记忆账本和工件指纹等基础机制，
不能据此声称已经修复真实支付系统。

## 先看任务状态怎样向前移动

| 阶段 | 系统现在知道什么 | 进入下一阶段前必须留下什么 |
| --- | --- | --- |
| 收到请求 | 用户描述了重复退款 | 基础代码版本、失败输入和允许修改范围 |
| 复现失败 | 同一业务退款在某条路径上出现两次 | 可重复命令、退出码和脱敏失败证据 |
| 形成补丁 | 某个假设得到代码支持 | 实际 Diff、依赖变化和补丁身份 |
| 完成验证 | 目标测试和约定门禁已有结果 | 命令、环境、原始产物和已知缺口 |
| 暂停任务 | 当前步骤完成，但用户稍后继续 | 结构化任务检查点，而不只是聊天摘要 |
| 准备发布 | 补丁成为发布候选的一部分 | 代码、模型、Prompt、索引与策略的完整版本关系 |
| 逐步放量 | 影子或小流量正在运行 | 停止条件、监控、回滚包和负责人 |
| 处理历史影响 | 旧版本可能已经重复退款 | 外部状态查询、对账、用户补救和事件记录 |

表中每一行都区分“模型说已经完成”和“系统有证据确认完成”。这条区别贯穿整个任务。

## 第一段：修复的是外部效果，而不是调用次数

第一版失败假设可以是：

> 重试请求生成了新的幂等键，支付服务因此把它当成另一笔退款。

代码 Agent 要在固定代码版本上复现失败，找到退款 Handler、调用者、数据库约束和重试逻辑，再生成尽量小的补丁。
测试目标也不能只写“函数调用一次”。真正关心的是：同一笔业务退款经过重试、超时和恢复后，只产生一次外部效果；
不同退款则不会因为键冲突被错误合并。

这段工作在[代码 Agent：从失败证据到最小补丁](code-agent-workflow.md)中展开。你会学习：

- 怎样把自然语言请求改写为任务契约；
- 为什么代码检索不能只靠向量相似度；
- 怎样让编译器和测试成为下一条观察；
- 为什么生成代码必须在受限环境中执行；
- `pass@k` 能回答什么，不能当成什么线上指标。

完成这一段时，Agent 交付的是“某个补丁在某组条件下通过某些检查”，而不是“软件已经没有缺陷”。

## 第二段：暂停后恢复的是结构化任务状态

假设补丁已经生成，目标测试也已经通过。此时用户说“我晚点再继续”。系统需要保存：

```text
任务编号
基础代码版本 + 当前补丁或结果提交
当前阶段 + 已完成的状态迁移
复现命令 + 失败证据摘要
验证命令 + 结果摘要
待回答问题 + 待审批事项
外部操作提案、回执和结果未知项
预算、策略与工具版本
```

一段对话摘要很难可靠回答“测试是否真的执行”或“发布是否已经批准”。恢复时还要重新读取当前仓库和实际 Diff，
避免在代码已经变化后继续使用旧结论。

这段工作在[对话状态与长期记忆：暂停后怎样安全恢复](conversation-state-memory.md)中展开。它会拆开三种容易混淆的信息：

- 原始对话记录用于回看用户和 Agent 说过什么；
- 任务检查点用于恢复一个尚未完成的工作流；
- 长期记忆只保存用户预期未来仍会使用的稳定偏好。

仓库中的可执行示例会把“偏好中文”修正为“English”，并保留来源、作用域、过期时间和修正链。

## 第三段：发布必须绑定完整系统版本

代码修好后，线上结果仍然受到模型、Prompt、索引、工具策略和 Runtime 影响。只记录 Git 提交或模型名称，都无法完整解释
某次生产输出。

| 组成发布的部分 | 必须绑定的身份 |
| --- | --- |
| 代码与构建 | Git 提交、依赖锁文件和镜像摘要 |
| 模型层 | 模型、tokenizer、模板与量化版本 |
| 上下文层 | Prompt、示例、语料、索引和检索器版本 |
| 工具层 | 工具 Schema、权限策略和审批规则版本 |
| 运行层 | 生成配置、Runtime 和路由版本 |

输出、工具回执、Trace、评测报告和发布决定，都要引用由这些身份共同组成的同一个发布编号。

这段工作在[LLMOps：把确切修改绑定到发布与回滚](llmops-release.md)中展开。你会沿同一退款修复继续学习：

- 组件版本关系图和工件指纹分别解决什么问题；
- 一次请求的 Trace 怎样回到完整系统版本；
- 离线门禁、影子运行、小流量发布和全量之间怎样交接；
- 缓存、备用模型和回滚为什么也是产品行为；
- 为什么回滚代码只能改变未来请求，撤销不了已经发生的重复退款。

## 一次交付最终要回答七个问题

任务完成时，不应只留下“Agent 说已经修好”。交付记录要能回答：

1. 哪个基础版本上复现了什么失败？
2. 哪个补丁或提交改变了哪条幂等契约？
3. 哪些命令在什么环境运行，原始结果在哪里？
4. 暂停与恢复时，任务阶段、审批和未知外部结果怎样保存？
5. 发布版本绑定了哪些代码、模型、Prompt、工具和索引？
6. 哪个门禁允许进入小流量，哪些信号会停止或回滚？
7. 如果重复退款已经发生，谁查询外部状态并负责补救？

前六项让未来请求走向正确版本。第七项处理旧版本已经造成的现实影响，两者不能互相替代。

## 本仓库能运行哪些基础验证

三篇专题页对应三组可执行基础：

| 专题 | 实现与测试 | 当前证据能支持什么 |
| --- | --- | --- |
| 代码修复评测 | `pass_at_k` 与 `tests/test_code_metrics.py` | 组合公式和输入边界符合仓库定义 |
| 状态与记忆 | `ConversationMemoryLedger` 与 `tests/test_conversation_memory.py` | 来源、过期、修正、撤回和租户作用域不变量 |
| 发布身份 | `artifact_fingerprint` 与 `tests/test_llmops.py` | 清单中明确列出的 JSON 组件得到稳定指纹 |

运行：

```powershell
python -m pytest `
  tests/test_code_metrics.py `
  tests/test_conversation_memory.py `
  tests/test_llmops.py -q
```

这些实现没有组成真实大型仓库修复、持久化记忆服务、跨副本并发系统或生产发布平台。它们适合学习并验证局部契约，
真实系统还需要对应环境、工作负载和组织流程的证据。

## 自测

1. 为什么“请求只发送一次”不足以证明没有重复退款？
2. 为什么暂停长任务时不能只保存一段对话摘要？
3. 模型版本相同时，哪些其他组件仍可能让线上行为变化？
4. 回滚代码后，为什么还要单独查询支付服务并对账？
