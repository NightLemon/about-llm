# 代码模型、对话与 LLMOps

## 代码任务

代码 LLM 处理补全、生成、解释、重构、测试、检索和修复。代码具有可执行反馈，但“能编译”远低于正确：要测试功能、边界、安全、性能和兼容性。

### 上下文构建

仓库级任务需要符号、引用、调用图、构建配置、测试和版本历史。按导入/符号检索比盲目塞整个仓库更有效；保留文件路径和行号。修改前读取局部约定与现有测试，生成 patch 而不是整文件覆盖。

### Fill-in-the-middle

代码补全常同时给前缀和后缀，通过特殊 token 训练 FIM。它比纯左到右更适合光标中间编辑。部署必须使用模型对应模板。

### 执行安全

生成代码在隔离容器/沙箱运行，限制 CPU、内存、时间、网络、文件系统和秘密。依赖安装也可能执行恶意脚本；锁定来源和版本。测试失败是反馈，不代表允许模型随意扩大权限。

### 评价

使用单元/集成测试、静态分析、类型检查、编译、mutation testing 和人工 review。Pass@k 必须注明候选数与采样。基准答案可能只覆盖表面功能；生产改动还测回归和安全。

## 对话系统

会话状态包含用户目标、已确认事实、待办、工具结果和权限，不应只靠原始聊天历史。长会话采用：

- 最近消息原文；
- 结构化状态；
- 可回溯摘要；
- 按需检索旧轮次；
- 用户可管理的长期记忆。

摘要会误写，应保存来源；事实有时间和置信度；“用户喜欢 X”与“本次请求 X”不能混为永久偏好。打断、纠正和话题切换需更新状态。

## LLMOps 版本轴

一次输出由模型/权重、tokenizer/template、Prompt、检索语料/索引、Embedding、reranker、工具/schema、策略和采样共同决定。所有轴都要版本化并写入 trace，才能回放和归因。

## AI 产品交互设计

界面要校准信任，而不是用流畅动画制造确定性。明确区分模型生成、检索证据、工具已执行与仅仅建议；对时效/高风险主张展示来源、日期和可纠错入口。不要用没有校准依据的任意百分比伪装置信度。

渐进披露先给结论和关键限制，再允许用户查看证据、步骤、原文与日志。展示“为什么不能完成”以及下一步，而不是笼统报错。耗时 Agent 任务显示当前阶段、已用预算、可取消状态和即将发生的外部动作。

用户控制包括编辑/删除记忆、关闭个性化、管理数据保留、撤销操作和转人工。副作用确认应说明对象、范围、金额/权限与可逆性，避免诱导式默认按钮。

可访问性覆盖键盘、屏幕阅读器、颜色对比、字幕/转录、文本缩放与认知负担。流式输出要避免焦点跳动和过度朗读；图像/图表生成替代文本。多语言界面同时测试模型质量、布局和安全策略，不能只翻译按钮。

研究用户行为时关注自动化偏见、确认偏误和技能退化。通过可编辑草稿、证据核对和适时摩擦让人保持实质控制，而不是名义上的“human in the loop”。

### Prompt 与数据管理

Prompt 视为代码：review、测试、版本、回滚，秘密从配置注入而不写入仓库。评测集视为产品资产：数据 lineage、访问权限、去重、标签协议和变更历史。

### 发布流程

离线门禁 → shadow 流量 → canary → 分阶段扩大 → 全量。检查质量、安全、延迟、成本和分群回归。配置更新也走同一流程，不能以“只是改一句 Prompt”跳过审查。

### 反馈闭环

显式点赞/踩有选择偏差，隐式点击/停留不等于正确。记录用户纠错、人工升级和任务结果，去除敏感数据并抽样标注。不要把线上原始反馈自动回灌训练，避免数据投毒和自我强化。

## 自测

1. 仓库级代码修复为什么只检索语义相似文件不够？
2. 对话摘要写错用户偏好时，应如何发现和纠正？
3. 模型权重没变，哪五类组件仍可能造成线上质量变化？
4. 如何设计界面，让用户区分“模型建议调用工具”和“工具已经执行”？
