退款补丁已经通过目标测试，任务检查点也保存完整。现在团队准备发布。

如果发布记录只写 `model=gpt-x` 或一个 Git 提交，线上出错时仍然无法回答：哪个 Prompt 触发了调用、哪个工具 Schema 接受了参数、
检索用了哪版索引、哪个 Runtime 负责重试。LLMOps 的第一步，是把这些共同决定行为的组件绑定成一次发布。

## 第一步：区分开发结果和发布结果

代码 Agent 交付的开发证据包括：

```text
基础代码版本
补丁或结果提交
命令、环境与测试输出
审阅决定
依赖和迁移变化
已知限制
```

发布一个 LLM 应用时，还要加入模型、上下文、工具和运行配置：

| 组成发布的部分 | 必须绑定的身份 | 只漏掉这一项会怎样 |
| --- | --- | --- |
| 代码与构建 | Git 提交、依赖锁文件、镜像摘要 | 无法确认线上二进制来自哪份源码 |
| 模型层 | 模型、tokenizer、模板、量化版本 | 同名模型仍可能采用不同输入格式或数值路径 |
| 上下文层 | Prompt、示例、语料、索引、检索器 | 模型不变时，答案仍可能因证据和提示变化 |
| 工具层 | 工具 Schema、权限策略、审批规则 | 同一参数可能获得不同执行权限 |
| 运行层 | 生成配置、Runtime、路由 | 采样、重试、缓存和备用路径无法解释 |

输出、工具回执、Trace、评测报告和发布决定，都应引用由这些身份共同组成的同一个发布编号。

图中每个节点使用不可变版本或摘要，连线记录兼容关系。例如，旧工具 Schema 可能无法与新 Prompt 配合；即使两者各自有
版本号，错误组合仍会失败。

这张关系图常被称为 Artifact Graph。中文可以直接理解为“本次发布的组件版本关系”。

## 第二步：工件指纹绑定清单，不替代清单

仓库的 `artifact_fingerprint` 会把明确给出的 JSON 组件按稳定字段顺序编码，再计算 SHA-256：

```python
from about_llm.llmops import artifact_fingerprint

first = artifact_fingerprint({"model": "m1", "messages": ["system", "user"]})
second = artifact_fingerprint({"messages": ["system", "user"], "model": "m1"})
assert first == second
```

映射字段换一个插入顺序，指纹保持相同；消息序列的顺序变化，指纹则应变化。

指纹只绑定清单里真正列出的内容。清单漏掉工具策略时，再稳定的哈希也无法识别策略变化。它也不证明远程供应商执行了
哪份模型，更不能说明两个版本语义相同。远程执行身份需要供应商回执、请求记录或其他匹配证据。

## 第三步：一次请求的 Trace 要能回到发布版本

退款请求的 Trace 至少关联：

- 请求、用例、时间和经过假名化的租户或用户身份；
- 模型、供应商、版本、tokenizer 和模板；
- 渲染后 Prompt 的摘要，以及按隐私策略保留的消息；
- 检索查询、结果、来源、索引和访问控制决定；
- 工具提案、参数校验、审批、执行与回执；
- 生成配置、结束原因和用量；
- 分阶段延迟、重试与缓存命中；
- 输出、评测、安全决定、错误和最终任务状态。

质量下降时，先找到发生变化的组件，再决定修改什么。模型权重保持不变时，代码、模板、索引和检索器仍可能引入回归。
工具 Schema、缓存、Runtime 和流量构成也是独立变量。

Trace 也包含敏感数据。用户编号和完整 Prompt 不适合作为指标标签；它们应进入访问受控的 Trace 或对象存储，并按字段脱敏、
设置保留期和采样限制。“为了可观测”不是永久保存所有用户输入的理由。

## 第四步：离线门禁决定能否进入真实流量

退款修复可以按下面的顺序形成发布决定：

1. 冻结包含代码提交的候选组件版本关系；
2. 在固定用例上运行功能、质量、安全和效率评测；
3. 与当前生产版本做逐用例配对比较；
4. 检查关键租户切片，以及“重复退款必须为零”等硬性规则；
5. 保存原始输出、配置、测试与评测报告；
6. 由有权限的负责人批准进入影子运行，或一次性返回全部阻断原因。

权限泄露和重复外部副作用通常应作为硬性门禁。总体帮助性分数提高，不能抵消一次跨租户泄露或重复退款。

离线通过后，流量分阶段扩大：

| 阶段 | 用户影响 | 退款修复重点 |
| --- | --- | --- |
| 回放或影子运行 | 不执行真实用户副作用 | 比较新版本会不会提出重复退款 |
| 小流量发布 | 少量真实流量，可快速停止 | 检查真实重试、延迟和重复外部效果 |
| 逐步扩大 | 按租户、地区或用途增加 | 观察关键切片退化与容量 |
| 全量 | 全部目标流量，持续监控 | 保持回滚和事件响应能力 |

线上 A/B 还要检查样本比例、用户固定分桶、保护指标和预先定义的停止规则。点击与停留时间只是代理指标，
不能替代真实事务状态和安全评测。

## 第五步：监控要帮助定位，而不只是报警

| 观测面 | 退款修复中的代表信号 |
| --- | --- |
| 任务结果 | 退款完成、拒答、纠正、转人工和重复外部效果 |
| 系统性能 | 队列、TTFT、TPOT、端到端延迟、超时、429/5xx、OOM 和吞吐 |
| 成本 | 输入输出 Token、检索、工具、重试和每次成功退款成本 |
| 安全 | 权限拒绝、提示注入、越权执行、个人信息或密钥暴露、沙箱违规 |

监控项要绑定负责人、阈值、响应时限和动作。告警只能告诉团队“可能有问题”；关联发布版本与分阶段延迟，才能进一步判断
问题发生在模型、代码、索引、工具还是基础设施。

## 第六步：缓存和备用路径也会改变结果

缓存身份至少覆盖：

- 回答与前缀缓存：模型、模板、Prompt、输入、生成参数、租户和策略；
- 检索缓存：语料、索引、检索器与访问控制；
- 失败或空结果：设置较短且有依据的过期时间，避免短暂故障长期固化；
- 模型或索引更新：明确让不兼容的旧缓存失效；
- 高风险输出：不跨身份共享。

语义缓存可能把措辞相似、但权限、金额或否定含义不同的请求合并。退款等高风险操作不能只靠向量相似度复用结果。

不同故障也不能共用一句“自动切换”。供应商 429、工具超时、检索失败、Schema 无效、安全分类器不可用和 GPU OOM，
需要各自的停止、重试、降级或转人工策略。

备用模型可能使用不同 tokenizer、工具协议和安全能力。它本身就是另一条发布路径，需要独立评测、监控和 Trace。

## 第七步：回滚改变未来，补救处理过去

一次 LLM 应用回滚可能涉及：

- 代码和构建镜像；
- 模型、tokenizer 与模板；
- Prompt、示例和生成配置；
- 语料、索引、检索器和缓存失效；
- 工具 Schema、权限策略和 Runtime。

切回旧版本只能改变未来请求。已经发生的重复退款仍然存在于支付服务中，需要查询权威状态、对账、通知用户并执行前向修复
（forward fix）。这一过程属于事件响应，而不是普通发布回滚。

退款结果未知时也不能盲目重试。先用稳定业务效果编号查询远端；确认没有应用时再决定重放，确认已经应用时则修复本地状态。

## 第八步：反馈进入训练前还要重新治理

点赞和点踩存在选择偏差，点击与停留时间受界面影响，用户主动纠正更接近任务结果但仍然不完整。反馈管线要记录：

- 用户同意和允许用途；
- 脱敏、垃圾与投毒检测；
- 抽样和标签规则；
- 来源链以及训练、验证、测试的隔离；
- 删除和撤回如何传播。

线上输出无条件回灌训练，会把旧模型错误、攻击内容和选择偏差继续带入下一版。

## 第九步：界面也要呈现真实任务状态

退款界面应区分模型建议、检索证据、工具提案、等待审批、已经执行、执行失败和结果未知。流畅动画或没有校准依据的
“97% 置信度”，无法把未知结果变成确定事实。

用户至少应能：

- 查看、更正和删除长期记忆，或关闭个性化；
- 暂停或取消长任务；
- 在副作用发生前查看对象、金额、范围和可逆性；
- 撤销工具与账户访问；
- 导出或删除数据；
- 转人工并提出申诉。

审批要绑定具体对象和参数，一个“确认”按钮不能批准未来所有退款。系统无法完成时，应说明缺少什么、已经完成什么、
当前是否存在结果未知的操作，以及安全的下一步。

可访问性同样属于正确性。界面应支持键盘、屏幕阅读器、清晰焦点、文本缩放和较低认知负担。流式文字不应让每个 Token
抢夺焦点或被重复朗读。多语言版本还要重新检查模型行为、安全、排版、输入法和文化语境。

## 运行仓库中的发布身份验证

```powershell
python -m pytest tests/test_llmops.py -q
```

这些测试验证显式 JSON 组件的稳定序列化和指纹变化。它们没有构建容器、部署模型、发送真实流量或执行生产回滚，
也没有证明清单已经包含所有重要组件。

把本页与[代码修复闭环](code-agent-workflow.md)和[对话状态与长期记忆](conversation-state-memory.md)连起来，
才能完整回答“一次退款修复怎样从失败现场走到上线”。

## 自测

1. 只记录模型名称和 Git 提交，为什么仍然无法重放一次线上行为？
2. 模型权重不变但质量下降时，应先比较哪些组件和 Trace 字段？
3. 为什么备用模型也需要独立的评测和发布身份？
4. 回滚代码后，已经发生的重复退款为什么还要做外部对账？
