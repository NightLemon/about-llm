请求 A 最终引用的 `S1`，最初只是一份 Markdown 文档中的一段话。它要先经过解析、切片、版本更新和权限写入，
才能成为检索器可见的候选。任何一步丢失表格、切断定义或残留旧版本，后面的 Embedding、重排模型和生成模型都很难补救。

## 先让一份真实来源走完整条链

运行：

~~~powershell
python projects/rag-foundations/rag_ingestion_walkthrough.py
~~~

程序读取项目正在使用的 `sample_corpus.jsonl`，选出下面这份来源：

| 字段 | 值 |
|---|---|
| 稳定来源 ID | `rag-security` |
| 租户 | `tenant-a` |
| 版本 | `1` |
| 可见主体 | `engineering` |
| 原始位置 | `kb://tenant-a/rag-security` |

### 版本 1：一份文档变成两个片段

`split_markdown` 按标题和空行切分后得到：

| 顺序 | 标题路径 | 片段 ID | 内容 |
|---:|---|---|---|
| 0 | `RAG 安全` | `chk_bd3e8a6757a7f05c07fdbcc4` | ACL 必须先于排序与上下文构建 |
| 1 | `RAG 安全 / 引用` | `chk_8d8a68a02d85a198190fc293` | 引用编号不能证明语义蕴含 |

两个片段都继承 `tenant-a`、`engineering` 和来源版本 `1`。标题不会直接混进正文，
但标题路径会参与片段 ID 的计算，并作为检索结果的结构信息保留下来。

### 版本 2：插入一段、修改一段、保留一段

walkthrough 随后构造版本 `2`：

1. 在开头插入“这份指南说明在线检索的权限边界”。
2. 在第一条规则中补充“候选召回”。
3. “引用编号不能证明语义蕴含”保持原文和标题路径不变。

增量计划的结果是：

| 动作 | 数量 | 为什么 |
|---|---:|---|
| 新 ID 写入 | 2 | 新段落和改写后的段落都有新的内容哈希 |
| 相同 ID 更新 | 1 | 引用段 ID 没变，但来源版本从 `1` 变成 `2`，顺序也从 1 变成 2 |
| 删除旧 ID | 1 | 版本 1 的 ACL 规则片段已被新内容替代 |
| 完全跳过 | 0 | 没有哪一行的全部 payload 都保持不变 |

这里最容易混淆的是：**稳定 ID 解决“这是不是同一个片段”，不决定“数据库这一行要不要更新”。**
引用段的 ID 在两个版本间保持为 `chk_8d8a68a02d85a198190fc293`，但它携带的来源版本和顺序发生了变化，
因此仍属于更新操作。

### 写入 SQLite 后，版本和权限继续生效

程序在临时 SQLite 数据库中真实执行版本 1 的首次写入和版本 2 的事务更新：

| 观察 | 结果 |
|---|---|
| 当前来源版本 | `2` |
| 匿名主体可见片段数 | 0 |
| `engineering` 可见片段数 | 3 |
| 再以“当前版本仍为 1”提交 | 拒绝：实际版本已经是 `2` |

这条主线运行了 Markdown 切片、增量计划、SQLite 事务和 ACL 读取。它没有生成 Embedding，
也没有更新远端关键词索引或向量库；跨存储的一致性仍要在目标系统中另外验证。

## 把这个例子推广到完整数据管道

RAG 的数据摄取应该是可以重放、比较和审计的数据产品，而不是一次性的“把文件塞进向量库”。完整链路通常是：

```mermaid
flowchart LR
    A["原始来源"] --> B["解析与规范化"]
    B --> C["恢复标题、表格和位置"]
    C --> D["切片并补充元数据"]
    D --> E["写入 ACL 与策略版本"]
    E --> F["关键词 / 向量索引"]
    F --> G["清单与来源追踪"]
```

每一阶段都要保留输入、输出、版本和错误。只保存最终向量，将无法回答“这个答案用了哪个文件版本”、
“为什么一段内容消失了”以及“删除请求是否传到了所有副本”。

## 先分清三种身份

一份资料更新时，下面三个值承担不同职责：

- `source_id`：业务来源，例如某个 Wiki 页面或对象存储 key，跨版本保持稳定。
- `source_version`：这次抓取的版本，可以来自 ETag、内容哈希、数据库 LSN 或显式修订号。
- `chunk_id`：一段可检索内容的身份，用于增量写入、引用和删除。

每个片段至少要知道自己属于哪个租户和来源、来自哪个版本、位于原文哪里，以及经过哪个解析器生成。
标题路径、时间、语言、ACL 和内容哈希也应随片段保存。ACL 是检索前的强制过滤字段，不是生成阶段的一句提示词。

### 稳定 ID 的取舍

用全局顺序号命名 `doc-17-chunk-8` 很简单，但在开头插入一段会使后续 ID 全变，缓存、引用和评测都会失效。
只用内容哈希也不够，因为同一标题下可能重复出现相同段落。本项目对以下组合做哈希：

\[
\text{chunk\_id}=H(tenant, source\_id, heading\_path, content\_hash, occurrence)
\]

这样，无关插入不会重命名未改段落；标题移动或正文变化会产生新 ID。同一标题下的重复内容再用出现次数区分。
来源版本有意不进入公式，因此版本提升不会让所有片段改名。版本仍作为 payload 保存，这正是 walkthrough 中“ID 不变但仍需更新”的原因。

## 解析不是纯文本提取

不同格式的主要风险不同：

| 来源 | 需要恢复 | 常见失败 |
|---|---|---|
| HTML/Wiki | 标题、列表、表格、链接、正文区域 | 导航和页脚混入正文 |
| PDF | 阅读顺序、页码、栏、表、脚注 | 双栏交错、扫描页为空 |
| Office | 标题层级、批注、表格、嵌入对象 | 模板文本重复 |
| 代码仓库 | 文件、符号、调用关系、版本 | 按固定字符切断函数 |
| 工单/聊天 | thread、作者、时间、附件 | 上下文与权限脱离 |

解析结果需要质量指标，例如非空页比例、字符异常率、表格单元格覆盖率、OCR 置信度和重复率。解析失败应进入 dead-letter queue，并能按解析器新版本重放。

### 规范化边界

可以统一换行、Unicode 形式和无意义空白；不要随意小写化代码、删除标点、把表格压成无结构字符串，或在保留证据位置之前清理页码。保存原始对象的不可变引用，规范化结果只是派生数据。

## 怎样决定片段大小

片段太小，定义和条件容易被切开，召回结果也会很碎。

片段太大，向量表示会混合多个主题；单个候选还会占用更多上下文，增加重排成本。因此不存在脱离任务的
“最佳 512 tokens”。选择大小时要同时考虑证据跨度、文档结构、Embedding 输入上限、生成窗口和延迟。

### 常用策略

1. 固定 token 窗口：容易建立稳定基线，适合连续文本；要记录重叠大小和真实 token 数。
2. 结构切分：按标题、段落、列表、代码符号或表格切，通常更容易保留完整语义。
3. 父子片段：用小片段召回，再把更大的上级片段交给模型。
4. 语义切分：根据相邻句向量的突变决定边界，成本更高，也会随模型版本变化。
5. Late chunking：先编码长上下文，再聚合片段内的 token 表示；需要模型和实现明确支持。

片段重叠可以提高边界处的召回，也会制造近重复候选并浪费上下文。应在带问题和证据标注的数据上比较片段大小与重叠，
而不是凭习惯选参数。

### 表格、代码和图片

表格应同时保留标题、列名、行范围和可读序列化；跨页表要先合并。代码更适合按 symbol/AST 切分，并附文件路径、签名和依赖。图片不能只保存 OCR：图表可能需要 caption、坐标区域或多模态 embedding。每类解析物都应能回链到原始位置。

## 增量更新与删除

一次完整抓取会产生“期望清单”，当前索引则提供“现有清单”。比较两份完整清单后：

- 新 ID 或任意 payload 字段发生变化：写入或更新；
- 旧清单存在、期望清单不存在：删除；
- ID 与全部 payload 都相同：跳过。

`plan_incremental_update` 只负责比较两份完整快照。它不知道“空的期望清单”究竟表示来源已删除，还是抓取任务失败；
因此调用者必须先判断输入是否完整。项目里的 SQLite 写入接口会拒绝零片段结果，并要求通过 `delete_source` 显式删除。
真实流水线还可以要求完整快照标志、来源墓碑记录或明确的事务边界。

walkthrough 的版本 2 正好说明 payload 比较的重要性：引用段的 ID 没变，但 `source_version` 和 `ordinal` 变化，
所以它进入更新集合而不是跳过集合。只比较 ID 会留下版本错误的旧记录。

同时更新关键词索引和向量索引时，可以先写入影子索引，完成完整性检查后原子切换别名，再延迟回收旧版本。
若目标系统无法原子切换，应让一次请求固定使用同一个索引版本，避免同一答案混用新旧片段。

### 删除的完整语义

删除范围不只包括主索引，还可能涉及向量缓存、重排缓存、回答缓存、日志副本、离线评测语料和备份保留策略。
隐私删除与普通业务下线可能有不同的时限要求；审计记录要能说明删除在哪些系统、什么时间生效。

## ACL 与多租户

`rag-security` 的 ACL 会复制到它的每个片段。walkthrough 写入版本 2 后，匿名主体读取到 0 个片段，
`engineering` 主体读取到 3 个片段。这说明权限不是页面展示时才临时补上的标签，而是片段存储和在线检索共同使用的数据。

在线查询的安全顺序是：认证用户 → 计算授权过滤器 → 生成授权候选 → 排序 → 组装上下文。
如果先取全局前 k 个结果再过滤，无权结果会挤掉有权结果，还可能通过分数、缓存或追踪记录泄露自身存在。

对 BM25 来说，“排序前过滤”也包括 IDF 和平均文档长度等集合统计。它们必须只基于授权候选，
否则越权正文即使没有进入结果，仍可能改变用户看到的分数。完整查询路径见[召回与重排](rag-retrieval.md)。

缓存键至少要绑定租户、权限策略版本、规范化查询、索引版本、检索配置和模型版本。ACL 变化后，旧缓存也要失效。
高基数 ACL 可以使用预过滤位图、分区索引或两阶段候选，但安全边界仍由模型外的授权系统负责。

## 怎样观察摄取管道是否健康

至少监控：

- 来源总数、成功数、失败数、隔离数和端到端更新延迟；
- 每格式解析耗时、空文档率、异常字符率；
- 片段数、长度分布、重复率和每个来源产生的片段数；
- 写入、删除、跳过的比例，以及没有对应来源的孤儿向量数；
- ACL 缺失率、未知租户和删除传播延迟；
- Embedding 吞吐、重试、模型版本和费用。

每个片段的来源链（lineage）都应从索引追溯到规范化文档、原始对象、解析器版本和具体任务运行。
抽样工具最好把原文与片段并排展示，让维护者能直接发现断句、表格错位和权限继承问题。

## 实验与验收

先确认 walkthrough 的固定行为：

~~~powershell
python projects/rag-foundations/rag_ingestion_walkthrough.py
python -m pytest `
  tests/test_rag_ingestion.py `
  tests/test_rag_sqlite_store.py `
  tests/test_rag_ingestion_walkthrough.py -q
~~~

你应该能解释以下结果，而不只是看到测试通过：

1. 引用段正文与标题路径未变，所以片段 ID 跨版本保持稳定。
2. 同一引用段的来源版本与顺序变化，所以数据库仍要更新它的 payload。
3. 被编辑的 ACL 规则得到新 ID，旧 ID 进入删除集合。
4. 旧版本写入被拒绝，避免并发任务覆盖新版本。
5. 匿名主体看不到任何 `rag-security` 片段，`engineering` 可以看到三个。

理解主线后，再修改脚本中的版本 2，观察这些边界：

- 只提升来源版本，正文不变：ID 都应保留，但 payload 需要更新。
- 修改 ACL：片段 ID 不变，权限 payload 必须更新。
- 加入超过 `max_chars` 的无空格段落：所有字符都应保留，且每段不超过上限。
- 让 Markdown 只剩标题：SQLite 写入应拒绝零片段结果，已有版本不得被删除。

生产验收还需要真实格式的固定样例、解析前后截图、并发更新、索引事务故障、删除时限和跨租户对抗测试。

## 面试追问

**为什么片段 ID 不直接包含来源版本？**
包含版本会让一次版本提升重命名所有未改内容。将版本作为 payload，片段 ID 只绑定内容与结构，
既能保留稳定身份，也能更新来源链；是否写入由完整 payload 的比较结果决定。

**为什么片段重叠不是越大越好？**
它可以提高边界证据的召回率，也会增加存储、近重复和上下文浪费，甚至让未经去重的指标显得虚高。
最终应结合证据召回、去重后的上下文质量和成本共同选择。

**如何在不停机的情况下重建 Embedding？**
让新模型写入带版本的影子索引，同时运行离线评测和线上影子查询。核对覆盖率与质量后，原子切换索引别名，
并保留快速回滚窗口。不要在同一个线上索引中原地混写两种向量。
