## 先填预测表，再运行

实验 7A 有一个"三个预测点"的问题块。**在运行任何命令之前**把它填完。
这个实验的推导部分放在预测表之后，就是为了让你先猜。

三个预测点大致围绕：

1. 分配了多少个块，最后一个块用了多少；
2. 复制一条序列（fork）时，块的引用计数怎么变；
3. 往共享块上写入时，会发生什么。

第 3 点是写时复制（copy-on-write）：多条序列可以共享同一个 prompt 的 KV 块，
直到某一条要写入时才复制。这是"共享 prefix 的多个请求"能省大量显存的原因。

## 触发容量耗尽

把块数调小，一直调到分配失败。你应该看到：

```text
KVCapacityError: append requires 1 free block(s), only 0 available
```

注意这是一个**明确的异常**：它在边界上给出可诊断的错误，
既区别于静默降级，也区别于让进程直接死掉的 OOM。这正是好的容量管理该有的样子。

第 18 天做服务基准时，你会把这个错误对应到 HTTP 层的一个具体状态码。

## 内部碎片

块大小固定，序列长度不固定，最后一个块必然有浪费。算一下：

```text
块大小 16，序列长度 100 → 用了 7 个块 = 112 个槽位，浪费 12 个
碎片率 = 12 / 112 ≈ 10.7%
```

块越大，碎片越多，但块表越小、管理开销越低。这是一个明确的取舍。
自己算几组不同块大小下的平均碎片率，找到你的直觉锚点。
