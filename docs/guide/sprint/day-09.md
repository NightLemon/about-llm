## 今天最重要的一条区分：pending ≠ failed

这是 Agent 工程里最贵的一个 bug 来源，和第 3 周会遇到的推理超时是同一类问题：

> 请求超时了，你**不知道**对方有没有执行。

如果把 `pending` 当成 `failed` 重试，你会付两次款、发两次邮件、建两条工单。
正确做法是把"无法证明未执行"单独记为一个终态，等待外部对账。

这条原则在本仓库里出现过三次（云 API 预算的 `uncertain`、Agent 的 `pending`、
推理服务的取消语义）。三次都指向同一件事：**分布式系统里"不知道"是一个必须建模的状态。**

## 第二条：审批与执行必须指纹绑定

用户审批的是"转账 100 元给 A"，执行的必须**恰好**是这件事。
如果审批之后参数还能变，审批就是装饰品。

实验 6 里有对应的测试。运行它，然后自己制造一个"审批后偷偷改参数"的场景，
看门禁是否拦住。拦不住的话，问题出在指纹覆盖的字段不全。

## 第三条：outbox 模式

业务状态变更和外部副作用不能在同一个事务里——数据库能回滚，发出去的 HTTP 请求不能。
outbox 的做法是：事务里只写一条"待发送"记录，由独立的投递器读取并发送。
代价是至少一次投递（at-least-once），所以**接收方必须幂等**。

## 必答题

1. 为什么 `pending` 必须和 `failed` 分开？各自的正确处理动作是什么？
2. 幂等键应该由调用方生成还是被调用方生成？
3. outbox 保证的是 at-least-once 还是 exactly-once？为什么后者做不到？
