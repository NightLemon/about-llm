## 时间盒

| 时段 | 内容 | 产出 |
|---|---|---|
| 上午 3h | 整理数据、重跑关键结论 | 可复现的结果集 |

| 下午 2h | 自我审查 | 定稿 |

参考 [`inference-serving`](../../practice/projects/inference-serving.md) 项目的组织方式。

## 报告的结构

```text
1. 目标与范围
   我要回答什么问题，不回答什么问题

2. 环境 identity
   硬件、驱动、框架版本、模型版本、数据版本
   （没有这一节，后面所有数字都不可复现）

3. 测量协议
   warm-up、重复次数、同步方式、负载形状、报告的分位数
   （这一节必须是测量之前写的那版）

4. 结果
   TTFT / TPOT / 吞吐三条曲线
   容量拐点
   失败终态表
   量化三档的性能 + 质量对照

5. 结论与建议
   每一条结论后面跟着支持它的具体数据

6. 证据边界 ★
   我没有测什么、这些结论在什么条件下会失效
```

## 第 6 节是这份报告最有价值的部分

整条速成路线反复练的就是这件事。回去看仓库里任何一个脚本的 `scope` 字段：

```text
cuda_or_gpu_kernel_executed: false
provider_usage_or_finish_reason_equivalence_proved: false
kernel_count_inferred_from_fx_or_export: false
```

这些"我没有验证什么"的声明，写起来毫无成就感，但它们是**区分工程师和调参者的分界线**。
一个能诚实说出自己结论边界的人，他说"是"的时候别人才敢信。

你的证据边界至少要覆盖：

- 只在一块 3070（8GB）上测过，没有多卡、没有其他架构；
- 只测过特定的 prompt / 输出长度分布；
- 质量评测的样本量与置信区间；
- 没有做长时间稳定性测试；
- 没有测过真实生产流量的到达模式。

## 自我审查清单

逐条打勾：

```text
[ ] 每一个数字都能指出它来自哪次运行
[ ] 每一条结论都有对应的数据，没有"看起来"「应该」这类词
[ ] 所有性能数字都注明了负载条件
[ ] 所有质量数字都带置信区间
[ ] 平均值没有被单独使用（都配了分位数）
[ ] 证据边界一节的篇幅不少于结论一节
[ ] 有人拿着这份报告和这台机器，能重现出同样的数字
```

最后一条是最硬的标准。
