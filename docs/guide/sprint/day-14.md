## 今天的核心交付：一张倒推表

不要按"技术 A、技术 B、技术 C"的顺序做笔记。按**症状**组织：

| 症状 | 先查什么 | 可能的手段 | 代价 |
|---|---|---|---|
| TTFT 高，TPOT 正常 | 排队时间 vs prefill 时间 | 连续批处理、chunked prefill、prefix 缓存 | 调度复杂度 |
| TPOT 高 | 是否 memory-bound | 量化、更好的 attention kernel、投机解码 | 质量 / 复杂度 |
| 吞吐低但延迟也不高 | GPU 利用率 | 增大 batch、连续批处理 | 单请求延迟上升 |
| 并发一上去就报容量错 | KV Cache 占用 | paged KV、GQA 模型、量化 KV | 实现复杂度 |
| 长 prompt 场景特别慢 | prefill 占比 | prefix 缓存、chunked prefill | 缓存命中率依赖负载 |
| 尾延迟（P99）差 | 是否有请求被反复抢占 | 调度策略、优先级 | 公平性 |

**自己填一遍这张表**，不要抄。填的过程中你会发现有些格子填不出来——那就是今天要补的地方。

## 一个必须建立的判断习惯

看到任何"某某技术提升 3 倍"的说法，问三个问题：

1. **提升的是哪个指标？** TTFT、TPOT、吞吐三者经常互相冲突。
   吞吐提升 3 倍，很可能伴随单请求延迟上升。
2. **在什么负载下？** 短 prompt 高并发和长 prompt 低并发是两个完全不同的世界。
3. **对照组是什么？** 和未优化的朴素实现比，和一个已经调好的基线比，
   数字可以差一个数量级。

这三个问题在第 18 天做基准时会直接用上。

## 必答题

1. 连续批处理（continuous batching）提升的是吞吐还是延迟？
2. 投机解码在什么情况下反而更慢？
3. prefix 缓存的命中率取决于什么？它在什么业务场景下几乎无效？
