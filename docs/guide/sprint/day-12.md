## 画一张带队列的时序图

不要只画"请求 → 模型 → 响应"。至少标出：

```text
HTTP 接入 → 鉴权/限流 → 请求排队 → 调度器选批
→ prefill → decode 循环（每步：调度 → 前向 → 采样 → 停止判定）
→ 流式发出 → 连接结束 → 资源释放
```

在每个箭头上标注：**这里可能等待多久，这里可能怎样失败。**

## 终态不只是"成功"和"失败"

列一张表，把所有可能的结束方式写全：

| 终态 | 触发条件 | 已消耗资源 | 是否该计费 |
|---|---|---|---|
| 正常 EOS | 模型输出结束符 | 全部 | 是 |
| 达到 max_tokens | 长度上限 | 全部 | 是 |
| 命中 stop string | 停止串匹配 | 全部 | 是 |
| 客户端断连 | 用户关闭连接 | 部分 | ？ |
| 服务端取消 | 超时 / 抢占 | 部分 | ？ |
| 容量拒绝 | 队列满 / 显存不足 | 极少 | 否 |

最后一列的两个问号是今天的思考题。它和第 9 天的 `pending ≠ failed`、
云 API 预算的 `uncertain` 是同一个家族的问题：
**客户端断连之后，GPU 上的计算停了吗？如果没停，谁付这个成本？**
